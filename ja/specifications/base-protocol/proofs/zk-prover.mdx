ZK プルーバーは、SP1 プログラムを使用して、チェックポイントの提案および異議申し立て向けのパーミッションレスな証明を生成する
オフチェーンサービスです。証明サービスはブロック範囲を指定したリクエストを受け付け、証明の状態を永続化し、
SP1 の証明インフラストラクチャにジョブを送信します。そして、呼び出し元が `AggregateVerifier` に送信できるレシートを
返します。

ZK パスはパーミッションレスです。正規の L1 および L2 の RPC へのアクセス、設定済みの SP1
バックエンド、L1 トランザクション署名者を用意できるオペレーターであれば誰でも、証明をリクエストし、有効な証明データをオンチェーンに送信できます。

## 責務 {#responsibilities}

準拠する ZK プルーバースタックは、以下の処理を実行します。

1. L2 ブロック範囲に対する証明リクエストを受け付ける。
2. 正規の L1、L2、およびビーコン RPC から witness 入力を生成する。
3. SP1 を使用してレンジプログラムを証明する。
4. Groth16 リクエストの場合、完了したレンジ証明を集約し、オンチェーンで検証可能な SNARK を生成する。
5. プロセスが再起動しても処理を再開できるよう、証明リクエストとバックエンドのセッション状態を永続化する。
6. 証明ステータスの確認とレシートの取得を gRPC 経由で提供する。
7. チャレンジャー、プロポーザー、および `ZKVerifier` が想定する形式でレシートをエンコードする。

ZK プルーバーは、ゲームの有効性を判断しません。証明する範囲の選択はプロポーザーとチャレンジャーが行い、
正規のルートも自ら再計算します。また、証明データをオンチェーンに提出する前に、
ゲームの状態を改めて確認します。

## 証明サービス API {#proving-service-api}

証明サービスは以下を提供します。

```text Proving Service API
ProveBlock(ProveBlockRequest) -> ProveBlockResponse
GetProof(GetProofRequest) -> GetProofResponse
```

`ProveBlock` は証明リクエストをキューに追加し、`session_id` を返します。`GetProof` は現在の
ステータスを返し、処理が完了している場合は、要求されたレシートのバイト列もあわせて返します。

### ProveBlock リクエスト {#proveblock-request}

`ProveBlockRequest` には以下のフィールドが含まれます。

| Field                       | 意味                                                                  |
| --------------------------- | ------------------------------------------------------------------- |
| `start_block_number`        | 範囲の信頼された開始状態となる出力ルートを持つ L2 ブロック。                                    |
| `number_of_blocks_to_prove` | `start_block_number` 以降に証明する L2 ブロックの数。                             |
| `sequence_window`           | witness 生成用の L1 ヘッドを導出する際に使用する L1 ブロックの先読み数 (任意) 。                  |
| `proof_type`                | `PROOF_TYPE_COMPRESSED` または `PROOF_TYPE_SNARK_GROTH16`。             |
| `session_id`                | 冪等なリクエストに使用する、呼び出し元が指定する UUID (任意) 。                                |
| `prover_address`            | 他の送信者による証明のリプレイを防ぐために Groth16 ジャーナルにコミットされる L1 アドレス。Groth16 では必須です。 |
| `l1_head`                   | witness 生成に使用する、32 バイトの 16 進数形式の L1 ブロックハッシュ (任意) 。                 |

`session_id` を指定した場合、同じ UUID による重複リクエストには既存のセッションが返されます。これにより、
チャレンジャーは `(game address, invalid checkpoint index)` から決定論的にセッション ID を導出でき、
プロセスが再起動しても安全にリトライできます。

証明ジャーナルを、すでにオンチェーンにコミットされている特定のゲームコンテキストと一致させる必要がある場合
(既存のゲームに対する紛争証明など) 、呼び出し元は `l1_head` を指定します。省略した場合、サービスは
L2 ブロックの L1 origin に、リクエストまたはサービスで設定されたシーケンスウィンドウを加えて L1 ヘッドを導出します。
これは、呼び出し元がまだ L1 ヘッドにコミットしていない新規プロポーザルに適した方法です。

`PROOF_TYPE_SNARK_GROTH16` では `prover_address` が必須です。集約プログラムはこのアドレスを
ジャーナルダイジェストにコミットし、`AggregateVerifier` は証明を受け入れる前に同じダイジェストを再検証します。
これにより、Groth16 レシートはそれを要求した L1 送信者に紐付けられます。

### 証明タイプ {#proof-types}

このサービスでは、次の2種類の証明タイプをサポートしています。

| 証明タイプ                      | バックエンドセッション      | 結果                                  |
| -------------------------- | ---------------- | ----------------------------------- |
| `PROOF_TYPE_COMPRESSED`    | `STARK`          | 圧縮された SP1 レンジ証明。                    |
| `PROOF_TYPE_SNARK_GROTH16` | `STARK`, `SNARK` | レンジ証明と、オンチェーンでの利用に適した Groth16 集約証明。 |

`PROOF_TYPE_SNARK_GROTH16` の場合、サービスはまずレンジプログラムを圧縮 STARK
セッションとして送信します。このセッションの完了後、集約プログラムを Groth16
SNARK セッションとして送信します。

## リクエストのライフサイクル {#request-lifecycle}

証明リクエストは、リクエストとアウトボックスエントリが永続化された時点で `CREATED` 状態から始まります。
次に、ワーカーがアウトボックスタスクを取得し、リクエストを `PENDING` に移行させたうえで、バックエンド処理の準備と送信を行います。
バックエンドセッションが 1 つ以上作成されると、リクエストは `RUNNING` になります。
証明タイプに必要なすべてのセッションが完了し、レシートのバイト列が保存されると、リクエストは `SUCCEEDED` になります。
一方、検証、witness の生成、バックエンドへの送信、バックエンドでの実行、レシートのダウンロード、またはリトライによる復旧のいずれかが
恒久的に失敗した場合は `FAILED` になります。

バックエンドセッションは、証明リクエストとは別に、独自に `RUNNING`、`COMPLETED`、`FAILED` の状態を管理します。
compressed リクエストは、すべての STARK セッションが完了した時点で成功となります。Groth16 リクエストは、STARK セッションと SNARK セッションの
両方が完了して初めて成功となります。いずれかのセッションが失敗した場合、親リクエストも失敗します。

## レシートの取得 {#receipt-retrieval}

`GetProofRequest` には次のフィールドが含まれます。

| フィールド          | 意味                                               |
| -------------- | ------------------------------------------------ |
| `session_id`   | `ProveBlock` が返す UUID。                           |
| `receipt_type` | レシート種別のセレクター (省略可) 。デフォルトは `RECEIPT_TYPE_STARK`。 |

レシート種別セレクターには次の値を指定できます。

| レシート種別                        | レスポンスのバイト列                                              |
| ----------------------------- | ------------------------------------------------------- |
| `RECEIPT_TYPE_STARK`          | レンジ証明のシリアライズされた SP1 proof-with-public-values。           |
| `RECEIPT_TYPE_SNARK`          | 集約証明のシリアライズされた SP1 proof-with-public-values。            |
| `RECEIPT_TYPE_ON_CHAIN_SNARK` | 保存済みの SNARK レシートから SP1 Groth16 検証器向けに抽出したオンチェーン証明のバイト列。 |

リクエストが `CREATED`、`PENDING`、`RUNNING` のいずれかの状態にある間、`GetProof` は空のレシートバイト列を返します。
失敗したリクエストに対しては、`STATUS_FAILED` と保存済みのエラーメッセージが返されます。成功レスポンスには必ず
空でないレシートバイト列が含まれます。保存済みのリクエストが `Succeeded` であっても、要求された種別の
レシートが存在しない場合、`GetProof` は空の成功レスポンスではなく gRPC `NOT_FOUND` を返します。

返されたレシートバイト列を `AggregateVerifier` の証明フォーマットでラップするのは、呼び出し側の責任です。
チャレンジ、無効化、追加証明の提出を行う場合、呼び出し側はレシートの前に ZK 証明タイプの
バイトを付加します。ゲームを初期化する場合は、`initializeWithInitData()` が要求する L1 origin フィールドも
呼び出し側で含めます。検証器側のフレーミングについては [Contracts](/ja/specifications/base-protocol/proofs/proof-contracts) を参照してください。

## バックエンドモード {#backend-modes}

証明サービスは、以下のバックエンドモードをサポートしています。

| モード       | 用途                                                      |
| --------- | ------------------------------------------------------- |
| `mock`    | witness を生成せずに、ローカルテスト用のダミーのレシートを生成します。                   |
| `cluster` | Redis または S3 にアーティファクトを保存し、セルフホストの SP1 クラスターにジョブを送信します。 |
| `network` | 設定されたフルフィルメントポリシーに従って、SP1 Network にジョブを送信します。           |

`cluster` バックエンドと `network` バックエンドの witness 生成パスは共通で、異なるのは送信、
ポーリング、アーティファクトの取得のみです。`mock` バックエンドでは、witness 生成が完全にスキップされます。

## SP1 レンジプログラム {#sp1-range-program}

レンジプログラムは、連続したブロック範囲における Base L2 の状態遷移を証明します。stdin
には以下の内容が含まれます。

```text Range Program Stdin
rkyv(DefaultWitnessData)
intermediateRootInterval
```

このプログラムは、witness からプリイメージオラクルとビーコン blob プロバイダーを再構築し、
Ethereum DA witness エグゼキューターを実行したうえで、`BootInfoStruct` をコミットします。

コミットされるブート情報には、以下の内容が含まれます。

| フィールド               | 意味                                |
| ------------------- | --------------------------------- |
| `l2PreRoot`         | 信頼済みの開始 L2 ブロックの出力ルート。            |
| `l2PreBlockNumber`  | 開始 L2 ブロック番号。                     |
| `l2PostRoot`        | 要求された範囲の実行後の出力ルート。                |
| `l2BlockNumber`     | 終了 L2 ブロック番号。                     |
| `l1Head`            | 導出データの取得に使用する L1 ブロックハッシュ。        |
| `rollupConfigHash`  | 実行時に使用されたロールアップ設定のハッシュ。           |
| `intermediateRoots` | 中間ルート間隔ごとにサンプリングされた出力ルート (順序付き) 。 |

最後の中間ルートは、証明対象範囲の終了 L2 ブロックに対応していなければなりません。

## SP1 集約プログラム {#sp1-aggregation-program}

集約プログラムは、完了したレンジ証明を、オンチェーン検証で使用されるジャーナルダイジェストに
変換します。入力は次のとおりです。

```text Aggregation Program Inputs
AggregationInputs              (sp1_zkvm::io::read)
L1 headers (CBOR-encoded)      (sp1_zkvm::io::read_vec)
compressed range proofs        (SP1 proof-input channel)
```

圧縮されたレンジ証明は、単なる stdin のバイト列ではなく SP1 の証明入力メカニズムを介して渡され、
プログラム内で `sp1_lib::verify::verify_sp1_proof` によって検証されます。

`AggregationInputs` には、レンジのブート情報、最新の L1 チェックポイントヘッド、レンジプログラムの
検証鍵、およびプルーバーのアドレスが含まれます。

集約プログラムは次の点を検証します。

1. レンジのブート情報が少なくとも 1 つ存在すること。

2. 隣接するレンジのブート情報が連続していること。

   ```text
   previous.l2PostRoot == next.l2PreRoot
   previous.l2BlockNumber == next.l2PreBlockNumber
   ```

3. すべてのレンジが同一の `rollupConfigHash` を使用していること。

4. すべての圧縮されたレンジ証明が、提供されたレンジ検証鍵で正しく検証されること。

5. 提供された L1 ヘッダーが連結されたチェーンを形成し、その末尾が `latest_l1_checkpoint_head` であること。

6. すべてのレンジの `l1Head` がそのヘッダーチェーンに含まれていること。

その後、プログラムはすべての中間ルートを平坦化し、単一の集約出力を構築します。

```text Aggregate Output Fields lines wrap expandable
proverAddress
l1Head
l2PreRoot
startingL2SequenceNumber
l2PostRoot
endingL2SequenceNumber
intermediateRoots
rollupConfigHash
imageHash
```

`imageHash` は、レンジプログラムの検証鍵に対するコミットメントです。集約プログラムは、次の値をコミットします：

```text Committed Journal Digest
keccak256(abi.encodePacked(AggregationOutputs))
```

このダイジェストは、`AggregateVerifier` が ZK 証明の検証用に組み立てるジャーナルハッシュと一致します。
[Contracts](/ja/specifications/base-protocol/proofs/proof-contracts) の用語でいえば、`imageHash` は `ZK_RANGE_HASH` に相当し、`ZKVerifier` に設定される集約検証鍵は
`ZK_AGGREGATE_HASH` に相当します。

## ELF の再現性 {#elf-reproducibility}

SP1 の ELF バイナリは必要に応じてビルドされ、リポジトリにはコミットされません。リポジトリでは、期待される ELF の
SHA-256 ハッシュを `crates/proof/succinct/elf/manifest.toml` で固定しています。いずれかの SP1
プログラムに影響するコード変更を行う場合は、同じ変更内で ELF を再ビルドし、`manifest.toml` を更新しなければなりません。

レンジ検証鍵のコミットメント (`ZK_RANGE_HASH`) および集約検証鍵のハッシュ
(`ZK_AGGREGATE_HASH`) は、オンチェーンのセキュリティパラメータです。オペレーターは、証明サービスが使用するものと同じ ELF から導出した値を用いて、verifier
コントラクトをデプロイまたは設定しなければなりません。

## リトライ動作 {#retry-behavior}

このサービスは、論理的な証明リクエストを変更せずに、一時的な状態に対してリトライを行います。

| 状態                                      | 必要な動作                                                |
| --------------------------------------- | ---------------------------------------------------- |
| アウトボックスタスクがすでに取得されている                   | 重複したワーカーをスキップします。                                    |
| アクティブなセッションがないまま `PENDING` で停滞しているリクエスト | リトライ上限に達するまで、新しいアウトボックスエントリを作成して `CREATED` にリセットします。 |
| バックエンドのステータスポーリングでエラーが発生                | リクエストを `RUNNING` のままにし、次回以降のポーリングでリトライします。           |
| バックエンドの成功後に証明アーティファクトが取得できない            | セッションを `RUNNING` のままにするか、次回以降のポーリングでダウンロードをリトライします。  |
| バックエンドが処理の失敗または履行不能を報告                  | セッションと証明リクエストを `FAILED` にします。                        |
| STARK の完了後に Groth16 の第 2 段階の送信が失敗       | 証明リクエストを `FAILED` にします。                              |

呼び出し元は、保存済みの当該リクエストについて、`FAILED` を終端状態として扱う必要があります。引き続き証明が必要な場合、
呼び出し元は決定論的な `session_id` を使用して、同じ論理リクエストを送信またはリトライしてください。

## サービスのライフサイクル {#service-lifecycle}

証明サービスは、起動時に次の処理を行います。

1. Postgres に接続します。
2. 必要に応じて、L1、L2、ビーコン RPC 用のレート制限付きローカルプロキシを起動します。
3. ロールアップ RPC からロールアップ設定を読み込みます。
4. レンジ証明と集約証明のそれぞれについて、証明鍵と検証鍵を計算します。
5. 設定されたバックエンドを初期化します。
6. アウトボックスプロセッサを起動します。
7. ステータスポーラーを起動します。
8. gRPC サーバーとリフレクションサービスを起動します。

アウトボックスプロセッサは、永続化されたリクエストをバックエンドセッションに変換します。ステータスポーラーは、実行中のセッションを同期し、
レシートをダウンロードします。また、必要に応じて Groth16 のステージ 2 を開始し、
停滞したリクエストを再試行するか、失敗として処理します。

## オペレーターが用意する入力 {#operator-inputs}

ZK プルーバーサービスには以下が必要です。

* L1 実行 RPC エンドポイント
* L1 ビーコン RPC エンドポイント
* L2 実行 RPC エンドポイント
* ロールアップ RPC エンドポイント
* Postgres の接続設定
* SP1 バックエンドの設定
* クラスターモード用のアーティファクトストレージ設定
* ポーリング間隔、停滞したリクエストのタイムアウト、リトライ上限
* メトリクスとロギングの設定

ネットワークモードでは、これらに加えて SP1 Network の署名者または KMS リクエスターの設定が必要です。クラスターモードでは、これらに加えて SP1 クラスターのエンドポイントと、アーティファクトストレージバックエンドを 1 つだけ設定する必要があります。

## オンチェーンでの想定動作 {#onchain-expectations}

ZK 証明のバイト列は、証明タイプ `ZK` として `AggregateVerifier` に送信されます。ゲームは提案または異議申し立てのコンテキストから
期待されるジャーナルを組み立て、設定済みの集約検証鍵を指定して
`ZKVerifier.verify()` を呼び出します。

有効な Groth16 レシートは、集約プログラムが期待されるジャーナルダイジェストをコミットしたことを証明します。
ただし、呼び出し側での状態チェックを代替するものではありません。プロポーザーとチャレンジャーは、証明データを送信する前に、
正規のルートを再計算し、ゲームの状態を改めて確認する必要があります。

## 安全性要件 {#safety-requirements}

ZK プルーバーの実装は、以下の安全性特性を維持しなければなりません。

* 呼び出し元から `l1_head` が提供された場合はそれを使用し、紛争証明がオンチェーンに保存されたゲームコンテキストと
  一致するようにします。
* Groth16 証明では `prover_address` を必須とします。この値は集約ジャーナルにコミットされるためです。
* 決定論的な `session_id` 値については、リクエストの作成を冪等に保ちます。
* 保存された SNARK レシートが正常にデシリアライズできない限り、オンチェーン用の SNARK バイト列を返してはなりません。
* バックエンドの非同期完了に依存する前に、バックエンドのセッションメタデータを永続化します。
* 検証鍵とオンチェーン設定が知らないうちに食い違うことのないよう、ELF ハッシュを固定します。
* RPC データの取得不能、バックエンドのポーリング失敗、アーティファクトのダウンロード失敗は、証明の有効性判定の結果ではなく、
  再試行可能なサービス状態として扱います。
