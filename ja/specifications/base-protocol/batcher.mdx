## 概要 {#overview}

バッチャー (バッチサブミッターとも呼ばれます) は、L2 のシーケンサーデータを L1 に投稿し、検証者 (verifier) が運用する導出パイプラインから利用できるようにする役割を担うエンティティです。バッチャートランザクションの形式 (およびそこに含まれるチャネル、フレーム、バッチの形式) は [derivation spec] で定義されています。データは L2 ブロックから構築され、その手順は L2 ブロックへ導出し直す際の逆順となります。検証者の観点から有効とみなされるのは、これらのルールに準拠したデータのみです。

バッチャーは、unsafe L2 ヘッド (シーケンス済みの最新ブロック) と safe L2 ヘッド (導出を通じて L1 上で確認された最新ブロック) との差分を監視します。まだ確認されていない unsafe L2 ブロックは、すべてエンコードして提出しなければなりません。バッチャーは L2 ブロックをチャネルにエンコードし、チャネルをフレームに分割したうえで、フレームを L1 トランザクションとして投稿します。その後、導出パイプラインがこれらのフレームを読み取ってチャネルを再構成し、バッチをデコードして元の L2 ブロックを復元します。

タイミングやトランザクションの署名方法は実装に依存します。データはいつでも提出できますが、検証者の観点から有効となるのは [derivation spec] のルールに一致するデータのみです。L2 側の safe / unsafe の状態は、データが L1 に提出または確認されても即座には更新されません。そのため、バッチャーの実装ではデータを重複して提出しないよう注意する必要があります。

## チャネルのライフサイクル {#channel-lifecycle}

チャネルは、バッチャーが使用するエンコードの単位であり、RLP エンコードされた L2 ブロックバッチを順序付けて圧縮したシーケンスです。チャネルは、送信待ちの L2 ブロックがあり、かつ現在開いているチャネルがない場合に開かれます。同時に開けるチャネルは最大 1 つです。前のチャネルが完全にクローズされ、そのすべてのフレームが L1 に送信されるまで、新しいチャネルを開いてはなりません。

チャネルは、以下のいずれかのクローズ条件を満たすまで、L2 ブロックバッチをブロック番号の厳密な昇順で蓄積します。次のバッチを追加すると圧縮後の出力サイズが blob の最大データ容量を超える場合、チャネルはクローズしなければなりません。これにより、データ可用性の格納先に対して大きすぎるペイロードをフレームが運ぶことはありません。また、蓄積を続けるとバッチの非圧縮 RLP バイト長の合計が `max_rlp_bytes_per_channel` を超える場合も、チャネルはクローズしなければなりません。これは、展開による増幅攻撃から検証者を保護するためのプロトコル上の制限です。いずれの場合も、超過の原因となるバッチは現在のチャネルには含めません。チャネルをクローズしたうえで、そのバッチを次のチャネルの最初のエントリとします。

さらに、チャネルはタイムアウト時にもクローズしなければなりません。チャネルが開かれたブロックから L1 チェーンが `max_channel_duration` を超える数の L1 ブロック分進んだ場合、チャネルをクローズし、そのフレームを直ちに投稿しなければなりません。これにより、チャネルが無期限に開いたままになるのを防ぎます。また、検証者は `channel_timeout` のウィンドウ内に完了しなかったチャネルをすべて破棄するため、データが破棄されないことも保証されます。

チャネルがクローズされると、その圧縮データは固定サイズのフレームに分割されます。各フレームには、最大 `max_frame_size` バイトの圧縮ペイロードと、フレームごとのヘッダーのオーバーヘッドが含まれます。生成されたフレームは、順序どおりに L1 への送信キューに追加されます。チャネルのブロック範囲(チャネルがカバーする L2 ブロック番号の連続した区間)はクローズ時に確定し、以降変更してはなりません。

## フレームの生成と順序 {#frame-production-and-ordering}

各フレームにはヘッダーが付与されます。ヘッダーには、所属するチャネルを識別する16バイトのチャネルID、チャネル内での位置を示すフレーム番号 (0から始まり単調増加する16ビット値) 、圧縮ペイロードの長さ、そしてそのフレームがチャネルの最後のフレームかどうかを示すブール値フラグが含まれます。さらに各チャネルの最初のフレームには、圧縮コーデックを識別する1バイトのバージョンバイトが含まれます。後続のフレームはすべて圧縮ペイロードのみで構成され、このようなプレフィックスは付きません。

チャネル内のフレームは、順番どおりにL1へ送信しなければなりません。フレーム `N` は、フレーム `N+1` より後にL1に現れてはなりません。導出パイプラインは、構成によっては順序が乱れたフレームの配信を許容する場合があります。ただしHoloceneハードフォーク以降は、最初のフレーム以外のフレームについて、フレーム番号がそのチャネルで直前に受信したフレームの番号よりちょうど1大きくない場合は破棄します。また、先行するチャネルがまだクローズされていないのに新しい最初のフレームを受信した場合も、そのフレームを破棄します。Holoceneの有効化後に正しく動作させるには、厳密に順序どおり配信する必要があります。

`is_last` フラグは、チャネルの最後のフレームにのみtrueを設定し、それ以前のすべてのフレームではfalseにしなければなりません。検証者は、`is_last` が設定されたフレームを受信して初めて、チャネルが完了したと見なします。`channel_timeout` の期間内に最後のフレームを受信できなかったチャネルは、検証者によって破棄されます。

## データ可用性 {#data-availability}

バッチャーは、フレームをバッチャートランザクションとしてL1に投稿します。宛先はバッチャーインボックスアドレスで、これはコントラクトではなく指定されたEOAです。各バッチャートランザクションはバッチャーの署名鍵で署名されていなければならず、署名から復元された送信者アドレスは、そのL1トランザクションが取り込まれた時点でL2システム設定に記録されている `batcherAddress` と一致しなければなりません。導出パイプラインはこのアドレスによってバッチャートランザクションを認証します。それ以外の送信者からのトランザクションは、内容にかかわらず無視されます。

L1のCancunアップグレード以降、主なデータ可用性メカニズムはEIP-4844のblobトランザクションです。各blobには、圧縮されたチャネルデータのフレームが1つ格納されます。blob 1つあたりの最大有効ペイロードは130,044バイトで、これが実質的な `max_frame_size` となります。バッチャーは、圧縮後のペイロードがこの上限を超えるフレームを生成してはなりません。

あるチャネルのすべてのフレームは、そのチャネルの最初のフレームが取り込まれたブロックから `channel_timeout` L1ブロック以内にL1に取り込まれなければなりません。この期間内にチャネルが完成しない場合、導出パイプラインはそのチャネルについてバッファリングしたフレームをすべて破棄し、影響を受けたL2ブロックは新しいチャネルで再送信されなければなりません。バッチャーは、フレームがこの期限内に投稿されるよう、チャネルのサイズを調整し、送信スループットを管理しなければなりません。

## ブロックの連続性 {#block-continuity}

バッチャーは、L2 ブロックをブロック番号の厳密な昇順でエンコードします。オープン中のチャネルに追加する各ブロックは、直前にエンコードしたブロックの直接の子でなければなりません。つまり、その親ハッシュは最後にエンコードしたブロックのハッシュと一致しなければなりません。この不変条件により、チャネルが正規の L2 チェーンのうち、連続していて曖昧さのない区間を表すことが保証されます。

L2 チェーンで再編成 (reorg) が発生した場合、バッチャーは保留中のエンコード状態をすべて破棄しなければなりません。reorg は、直前に確認した先端と親ハッシュが一致しないブロックとして現れるか、ブロックソースからの明示的な reorg シグナルとして通知されます。破棄の対象には、現在オープン中のチャネル、送信キューに入っているがまだ完全には確認されていないチャネル、および送信中のトランザクションに関するすべての追跡情報が含まれます。reorg の後、バッチャーは新しい正規チェーンの先端から処理を再開します。reorg の時点ですでに送信中だった L1 トランザクションは放棄されます。それらが最終的に L1 に取り込まれたとしても、新しいチェーンと整合しないため、導出パイプラインによって無視されます。

各チャネルは、L2 ブロック番号の連続した、重複のない範囲をカバーします。後続チャネルのブロック範囲は、先行チャネルのブロック範囲が終わった位置から正確に始まらなければなりません。1 つの L2 ブロックが複数のチャネルに含まれてはならず、連続するチャネルの間でブロックを飛ばしてもなりません。

## シーケンサーのドリフトとスロットリング {#sequencer-drift-and-throttling}

導出仕様では、L2 のタイムスタンプが、そのオリジンブロックの L1 タイムスタンプよりどこまで先行できるかが制約されています。L2 ブロックのタイムスタンプは、L1 origin のタイムスタンプに `max_sequencer_drift` を加えた値を超えてはなりません。Fjord ハードフォークより前は、`max_sequencer_drift` はチェーンごとの設定パラメーターです。Fjord 以降は 1800 秒に固定されています。この上限を超えた場合、導出パイプラインはトランザクションリストが空のバッチ(デポジットのみのブロック)しか受け入れません。そのため、バッチャーは、タイムスタンプがドリフト上限を超えるブロックにユーザートランザクションを含めてはならず、これに合わせてシーケンサーと連携する必要があります。

シーケンサーのペースがバッチャーの L1 への送信能力を上回らないよう、バッチャーはデータ可用性のバックログを計測します。バックログとは、シーケンス済みでありながら、そのデータがまだ L1 上で確認されていない L2 ブロックの、エンコード後の合計サイズです。バックログが設定されたしきい値を超えると、バッチャーはシーケンサーにブロック生成レートを下げるよう通知します。スロットリングは段階的に行うこともできます。たとえば、バックログが小さければ緩やかな減速を要求し、大きければバッチャーが追いつくまでブロック生成を完全に停止させる、といった具合です。このフィードバック機構は導出パイプラインからは透過的であり、オンチェーンデータには一切反映されません。

## 圧縮 {#compression}

チャネルデータは、フレームに分割される前に圧縮されます。Fjord ハードフォークより前のチャネルは zlib 圧縮 (RFC 1950、辞書なし) を使用し、バージョンプレフィックスを持ちません。展開器は、ストリーム内の zlib マジックバイトによって形式を識別できます。Fjord 以降のチャネルは Brotli 圧縮 (RFC 7932) を使用し、各チャネルの最初のフレームでは、コーデックを識別するためのバージョンバイト `0x01` が圧縮ペイロードの直前に付与されます。バージョンバイトの下位ニブルは `0x08` または `0x0f` であってはなりません。これらの値は zlib のマジックヘッダーバイトと衝突し、旧来の展開器を誤動作させるためです。

圧縮率は入力内容によって変動するため、バッチャーはバッチをチャネルにエンコードしながら、圧縮後の出力サイズを先回りして見積もる必要があります。チャネルは、圧縮出力が `max_frame_size` を超えてからではなく、超える前に閉じなければなりません。一般的な手法として、実際の圧縮器と並行してシャドウ圧縮器を動かし、その出力サイズを上限値とみなす方法があります。この場合、シャドウの出力が上限に達した時点でチャネルを閉じます。これにより、バッチャーが blob に収まらないサイズのフレームを生成することはなくなります。

チャネルあたりの非圧縮 RLP の最大サイズ `max_rlp_bytes_per_channel` は、圧縮サイズの上限とは別に適用されます。この上限は、展開による増幅攻撃から検証者を保護するためのものです。小さな圧縮ペイロードが際限なく大きな非圧縮ストリームに展開されると、メモリを使い果たすおそれがあります。チャネルをデコードする検証者は、非圧縮出力がこの上限に達した時点で処理を停止し、残りのバッチは破棄されます。バッチャーは、すべてのバッチを確実に検証者に認識させるため、またプロトコルで定義された制限を守るため、バッチの非圧縮サイズがこの上限を超えないようにしなければなりません。

## 確認とブロックの削除 {#confirmation-and-block-pruning}

バッチャーは、送信した各フレームがL1ブロックに取り込まれるまで追跡します。フレームを格納したL1トランザクションを含むL1ブロックをバッチャーが観測した時点で、そのフレームは確認済みとなります。チャネルは、そのすべてのフレームがL1上で確認された時点で完全に確認済みとなります。

L2ブロックは、それを含むチャネルが完全に確認されるまで、バッチャーのpendingセットから破棄してはなりません。確認されるまでは、失われたフレーム (たとえば、L1のreorgによってトランザクションの取り込みが取り消された場合など) を再構築して再送信できるよう、それらのブロックを保持しなければなりません。バッチャーがチャネルに含まれるL2ブロックを解放できるのは、そのチャネルが完全に確認された後に限られます。

送信したフレームのL1トランザクションが取り込まれなかった場合、バッチャーはそのフレームと、同じチャネル内の後続のすべてのフレームを再送信しなければなりません。再送信するフレームは、元のフレームとバイト単位で同一でなければなりません。導出パイプラインはチャネルIDとフレーム番号でフレームを識別するため、内容の異なるフレームを再送信すると、再試行ではなく破損データとして扱われてしまいます。

## ハードフォークのルール {#hardfork-rules}

Fjord ハードフォークでは、チャネルのエンコード形式が変更されます。Fjord の有効化以降に開かれたチャネルは Brotli 圧縮を使用し、最初のフレームのペイロードの先頭にバージョンバイト `0x01` を付加しなければなりません (MUST) 。プロトコル上の上限 `max_rlp_bytes_per_channel` は Fjord の有効化時に大幅に引き上げられ、チャネルサイズの制約が緩和されます。Fjord の有効化前に開かれたチャネルは、フレームの投稿時期にかかわらず、すべてのフレームで Fjord 以前の形式を使用しなければなりません (MUST) 。

Holocene ハードフォークでは、フレーム層とバッチ層の両方に厳格な順序要件が課されます。フレーム層では、あるチャネルのフレームは連続して、かつ順序どおりに導出パイプラインへ渡されなければなりません (MUST) 。最初のフレーム以外のフレームが、そのチャネルで直前に確認されたフレームのすぐ次のフレームでない場合、そのフレームは即座に破棄されます。また、未完了のチャネルについて、最後のフレームが確認される前に新たな最初のフレームが到着した場合、そのチャネルは破棄されます。バッチ層では、チャネル内のバッチは L2 タイムスタンプの厳密な昇順に並んでいなければならず (MUST) 、タイムスタンプの重複は許されません。同じチャネル内で直前のバッチよりタイムスタンプが厳密に大きくないバッチがあると、そのチャネルは無効化され、チャネル内の残りのバッチはすべて破棄されます。これらのルールによってオンチェーン上の新たな義務が生じるわけではありませんが、Holocene の有効化以降、バッチャーにはフレーム配信の欠落や順序の入れ替わりが一切許されなくなります。
