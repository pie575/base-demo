  Denim により、`block.number` の進む速さが変わります。コントラクトでブロック数を基準に時間を計測している場合は、アクティベーション前に[ブロック番号に基づくコントラクトロジック](#block-number-based-contract-logic)を必ずお読みください。
</Warning>

## 概要 {#summary}

Denim は、Base のブロック生成を「2 秒ごとに 1 つの正規ブロック」から「1 秒あたり 5 つの完全な正規ブロック」へと変更します。200ms ごとの各ブロックは、それぞれ独自のブロック番号、ハッシュ、ステートルート、レシート、フォークチョイス更新を持ち、unsafe、safe、finalized のライフサイクルもブロックごとに管理されます。

Denim は [Flashblocks](/ja/specifications/flashblocks) に代わるものです。Flashblocks は、単一ブロックの pending 状態を増分更新として配信する仕組みです。Denim の展開に伴い、Base は Flashblocks の生成を停止し、代わりに 200ms ごとに正規ブロックを生成します。Flashblocks を使用しているアプリケーションは、正規ブロックおよび RPC ストリームへ移行する必要があります。

Denim では、Ethereum のブロックヘッダーと秒単位の `timestamp` は変更されません。1 秒未満の部分は BaseTime メタデータデポジットによって提供されます。これらの値を組み合わせることで、正規ブロックのタイムスタンプをミリ秒単位で完全に特定できます。

<Info>
  アプリケーションで Flashblocks を使用している場合は、必要な API の変更について [Flashblocks からの移行](/ja/upgrades/denim/migrate-from-flashblocks) を参照してください。
</Info>

## ブロック番号に基づくコントラクトロジック {#block-number-based-contract-logic}

<Warning>
  Denim により、Base のブロック生成は 2 秒ごとに 1 ブロックから、1 秒あたり 5 ブロックに変わります。実時間で見ると `block.number` は 10 倍の速さで進みますが、`block.timestamp` は従来どおり秒単位で進みます。ブロック数を時間の長さとして扱うコントラクトやオフチェーンシステムでは、アクティベーション後、その期間が本来の長さの 10 分の 1 に短縮されます。イミュータブルまたはアップグレード不可能なコントラクトに組み込まれたブロック数の定数は、アクティベーション後に再調整できません。
</Warning>

Denim のアクティベーション前に、ブロック数を時間に換算しているロジックがないか、コントラクトを監査してください。

| パターン                                                                       | Denim 後の影響                                                                                                                      |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `block.number - start >= N` で計測されるタイムロック、クールダウン、退出遅延                       | 本来の実時間の 10 分の 1 で経過します。                                                                                                         |
| ブロック単位で計測されるベスティング、エミッション、難易度のスケジュール                                       | 実時間で 10 倍の速さで完了または再調整されます。                                                                                                      |
| `block.number` が変わるたびにリセットされるブロックごとのレート制限や上限                               | 2 秒に 1 回ではなく 1 秒に 5 回リセットされるため、実質的な 1 秒あたりの上限が 10 倍になります。                                                                       |
| `expirationBlock = block.number + N` として設定される期限                            | 本来の実時間の 10 分の 1 で期限切れになります。                                                                                                     |
| ブロック単位のガバナンス投票遅延と投票期間 (デフォルトのブロック番号ベースの `clock()` を使用する `ERC20Votes` を含む)  | 投票期間が 10 分の 1 に短縮されます。保存済みのチェックポイントは引き続き正しい値を保ちます。                                                                              |
| Uniswap V3 形式の TWAP オラクル                                                   | アキュムレーターは秒単位で重み付けされるため、TWAP の値は引き続き正確です。ただし、固定の観測カーディナリティでカバーできる実時間の履歴はおよそ半分になるため、長期間を遡る `observe()` はより早い段階で `OLD` によりリバートします。 |

`block.timestamp` で時間を計測するロジックは影響を受けません。

以下の準備を行ってください。

* 再デプロイまたはアップグレードが可能な箇所では、ブロック数による期間を `block.timestamp` の比較に置き換えます。
* ブロック数がガバナンスで調整可能な場合は、アクティベーション時に 10 で割るよう計画します。
* ブロック数がイミュータブルで変更できない場合は、影響を評価し、アクティベーション前に移行を計画します。
* すでに 200ms ブロックを生成している [Vibenet](/ja/build-on-base/test-on-vibenet) で、変更後の挙動をテストします。

## 実行 {#execution}

### 完全なブロックタイムスタンプ {#full-block-timestamp}

Denim でも、`block.header.timestamp` は秒単位の Unix 時刻のまま変わりません。アクティベーション後のブロック `b` の完全なタイムスタンプは次のとおりです。

$$
T&#95;{ms}(b) = 1000 \times b.header.timestamp + b.tx[1].timestamp&#95;millis&#95;part
$$

`timestamp_millis_part` は、`tx[1]` にある BaseTime デポジットに格納されます。有効な値は `0`、`200`、`400`、`600`、`800` のみです。アクティベーション後の連続するブロックは、次の条件を満たします。

$$
T&#95;{ms}(child) = T&#95;{ms}(parent) + 200
$$

ブロックはスロットを飛ばすことができません。秒単位のヘッダー値とミリ秒部分は、同一の予定タイムスタンプから導出されなければなりません。実時間 (ウォールクロック時間) が決めるのは sequencer がビルドを開始するタイミングであり、そのブロックに割り当てられるタイムスタンプではありません。EVM の `block.timestamp` は、引き続き秒単位のヘッダー値となります。

### BaseTime メタデータデポジット {#basetime-metadata-deposit}

アクティベーション後は、すべてのブロックの `tx[1]` に正規の BaseTime 更新が含まれます。この位置は、`tx[0]` の L1 情報デポジットの直後で、ユーザートランザクションよりも前です。このデポジットは、ソースハッシュドメイン `3` によって現在のブロック番号に紐付けられます。

| フィールド        | 値                                                                               |
| ------------ | ------------------------------------------------------------------------------- |
| トランザクションタイプ  | デポジット (`0x7e`)                                                                  |
| ソースハッシュ      | ドメイン `3`、現在のブロック番号に紐付け                                                          |
| From         | `0xDeaDDEaDDeAdDeAdDEAdDEaddeAddEAdDEAd0001`                                    |
| To           | `0x4200000000000000000000000000000000000030`                                    |
| Mint         | `0`                                                                             |
| Value        | `0`                                                                             |
| ガスリミット       | `1,000,000`                                                                     |
| システムトランザクション | `false`                                                                         |
| Calldata     | `setTimestampMillisPart(uint16)` (セレクタ `0x86bdf394`、32 バイトに ABI エンコードされたミリ秒部分)  |

アクティベーション前のブロックには、このメタデータトランザクションも Engine のミリ秒フィールドも含めてはなりません。アクティベーション後、実装はトランザクションの位置、ソースハッシュ、送信者、受信者、mint、value、ガスリミット、システムフラグ、calldata の形式、およびラティス値を検証します。

### BaseTime プリデプロイ {#basetime-predeploy}

初期設計では、現在のブロックのミリ秒部分をプリデプロイ経由でコントラクトに公開します。

| プロパティ           | 値                                            |
| --------------- | -------------------------------------------- |
| プロキシ            | `0x4200000000000000000000000000000000000030` |
| 実装              | `0xc0D3C0d3C0d3C0D3c0d3C0d3c0D3C0d3c0d30030` |
| ストレージ           | スロット `0` に格納される `uint16` のミリ秒部分              |
| セッター            | `setTimestampMillisPart(uint16)`             |
| ミリ秒部分のゲッター      | `timestampMillisPart()`                      |
| 完全なタイムスタンプのゲッター | `timestampMs()`                              |

BaseTime デポジットは L1 ユーザーデポジットおよびユーザートランザクションよりも前に実行されるため、後続のすべてのトランザクションは更新後の値を読み取れます。

新規チェーンでは、リンク済みの BaseTime プリデプロイがジェネシス時にインストールされます。既存チェーンでは、予約済みアドレスに正規のプロキシランタイムがすでに存在し、Base ProxyAdmin を使用していますが、実装スロットは未設定です。そのため、アクティベーションまでは呼び出しがリバートします。

アクティベーション時には、トランザクションの実行前に、プロトコルが正規の BaseTime 実装をインストールして既存のプロキシにリンクします。その際、プロキシ管理者と、ガバナンスを通じてすでに設定されている実装はそのまま保持されます。

### Engine ペイロード属性 {#engine-payload-attributes}

Engine API は `BasePayloadAttributes` を使用します。これは、標準の `PayloadAttributes` のフィールドと Base 固有のフィールドを同一階層にフラット化したものです。

Denim のアクティベーション時点以降のペイロードでは、`BasePayloadAttributes.timestampMillisPart` が存在し、その値は `0`、`200`、`400`、`600`、`800` のいずれかでなければなりません (**MUST**) 。アクティベーション前は、このフィールドが存在してはなりません (**MUST NOT**) 。

`BasePayloadAttributes.transactions[1]` には BaseTime メタデータデポジットが含まれていなければなりません (**MUST**) 。このデポジットはプロトコルデポジターから BaseTime プリデプロイに送信されなければならず (**MUST**) 、その calldata には `setTimestampMillisPart(uint16)` の正規エンコーディングが含まれていなければなりません (**MUST**) 。エンコードされた値は `timestampMillisPart` と一致しなければなりません (**MUST**) 。

実行クライアントは、不正な形式の `forkchoiceUpdated` ペイロード属性を JSON-RPC の `Invalid params` (`-32602`) で拒否しなければなりません (**MUST**) 。また、BaseTime デポジットが欠落しているか無効な実行ペイロードは、`newPayload` の検証時に無効として報告しなければなりません (**MUST**) 。

ペイロード ID には `timestampMillisPart` が含まれるため、ミリ秒部分だけが異なるビルドにはそれぞれ別の ID が割り当てられます。このフィールドが存在しない場合、ペイロード ID は従来どおりの方法で計算されます。

既存の Engine のタイムスタンプフィールドは、引き続きすべて秒単位です。

### 検証 {#validation}

`forkchoiceUpdated` を処理する際、実行クライアントはコントラクトの状態を読み取らずに行えるチェックを実施します。Denim より前は、`timestampMillisPart` が存在してはなりません。Denim 以降は、これが存在し、かつ値が `0`、`200`、`400`、`600`、`800` のいずれかでなければなりません。ブロックの秒単位のタイムスタンプは、親ブロックのタイムスタンプより前であってはなりません。ブロックヘッダーにはミリ秒が保存されないため、厳密に 200ms 刻みで進んでいるかどうかは、クライアントが実行後にチェックします。

実行後、クライアントは、ブロックの完全なタイムスタンプが親ブロックのタイムスタンプのちょうど 200ms 後であることを検証**しなければなりません (MUST)&#x20;**。この要件を満たさないブロックは無効です。

## 導出 {#derivation}

### スケジュールに基づくタイムスタンプ {#scheduled-timestamps}

アクティベーション後、導出パイプラインは Denim のアクティベーションスケジュールと L2 の絶対ブロック番号から、各ブロックのタイムスタンプを算出します。ミリ秒部分をバッチデータから読み取ることも、ローカルの実時間クロックから導出することもありません。シーケンスは次のとおりです。

`p (.000)` → `child (.200)` → `child (.400)` → `child (.600)` → `child (.800)` → `child (.000 in the next second)`

パイプラインは、スケジュールに基づくタイムスタンプを秒単位のヘッダータイムスタンプと BaseTime のミリ秒部分に分割したうえで、`tx[1]` の BaseTime デポジットを再構築します。

### ブロックのライフサイクル {#block-lifecycle}

sequencer は、選択された 200ms スロットごとに完全なブロックを構築・実行します。各ブロックはそれぞれ固有のハッシュ、ステートルート、レシート、Engine ペイロード、フォークチョイス更新を持ち、unsafe から safe、そして finalized へと至る独自のライフサイクルをたどります。

ブロックの先頭には、`tx[0]` に L1 情報デポジット、`tx[1]` に BaseTime メタデータデポジットが配置されます。その後に、ユーザートランザクションやその他の該当するトランザクションが続きます。この設計では、ペイロード属性、`tx[1]`、および BaseTime プリデプロイに書き込まれる値が、いずれも同じ計画上のミリ秒部分を表すことを想定しています。

## RPC {#rpc}

<Note>
  以下の RPC の動作は Denim で導入予定のものであり、本番環境のエンドポイントではまだ利用できません。
</Note>

### 秒単位との互換性 {#seconds-compatibility}

Denim でも、既存の `timestamp` JSON-RPC フィールドは引き続き Unix 秒で表されます。Engine のタイムスタンプ、トランザクション有効性のタイムスタンプ、`eth_call` のタイムスタンプ、および EVM の `block.timestamp` も、引き続き秒単位です。内部フィールドである `timestampMillisPart` は、RPC レスポンスでは公開されません。

Denim のロールアウト後、1 秒未満の更新を取得するには、正規のブロックレスポンスや `eth_subscribe("newHeads")` などのサブスクリプションを使用してください。Flashblocks のストリームは停止されます。

### ブロックおよびヘッダーのタイムスタンプ {#block-and-header-timestamps}

以下のレスポンスに、オプションの `timestampMs` フィールドが追加されます。この値は、ミリ秒単位の完全な Unix タイムスタンプを表す JSON-RPC の quantity としてエンコードされます。

* `eth_getBlockByHash`
* `eth_getBlockByNumber`
* `eth_getHeaderByHash`
* `eth_getHeaderByNumber`
* `eth_subscribe("newHeads")`

たとえば、42.200 秒時点のブロックの値は次のとおりです。

| フィールド         | 値        |
| ------------- | -------- |
| `timestamp`   | `0x2a`   |
| `timestampMs` | `0xa4d8` |

クライアントは、`timestampMs` を秒単位のフィールドから推定するのではなく、認証済みの BaseTime メタデータから導出します。過去のブロック本体やその BaseTime メタデータがプルーニング済みである場合や、その他の理由で利用できない場合、レスポンスに `timestampMs` は含まれません。

### トランザクションのタイムスタンプ {#transaction-timestamps}

以下のメソッドでは、マイニング済みトランザクションのオブジェクトにオプションフィールド `blockTimestampMs` が追加されます。

* `eth_getTransactionByHash`
* `eth_getTransactionByBlockHashAndIndex`
* `eth_getTransactionByBlockNumberAndIndex`

ブロックのレスポンスにネストされた完全なトランザクションオブジェクトも、マイニング済みトランザクションと同様に扱われます。保留中のトランザクションはまだ正規ブロックに含まれていないため、`blockTimestampMs` は返されません。

### ログおよびレシートのタイムスタンプ {#log-and-receipt-timestamps}

マイニング済みのログオブジェクトには、以下のメソッドから返される際に、オプションの `blockTimestampMs` が追加されます。

* `eth_getLogs`
* `eth_getFilterChanges`
* `eth_getFilterLogs`
* `eth_getTransactionReceipt`
* `eth_getBlockReceipts`
* `eth_subscribe("logs")`
* `eth_subscribe("transactionReceipts")`

レシートでは、このフィールドはレシートのトップレベルではなく、ネストされたログに含まれます。削除されたログは、元のブロックの出所情報とともに、元のブロックタイムスタンプを保持します。生成元ブロックの認証済み BaseTime メタデータが利用できない場合、ログではこのフィールドの値を推定せず、フィールド自体を省略します。

ブロックのレスポンスと同様に、プルーニング済みのトランザクションデータやログデータ、または出所情報を持たないトランザクションデータやログデータでは、`blockTimestampMs` が省略されます。これらのフィールドをオプションとしているのは、Denim 以前の履歴や、必要なボディデータを持たないクライアントも引き続き表現できるようにするためです。

### ツール {#tooling}

Foundry の `AnyRpcBlock` および `OtherFields` を経由する場合は、未知のブロックレベルの `timestampMs` を保持できますが、EVM の実行では引き続き秒単位が使用されます。素の Alloy の `AnyRpcHeader` は未知のフィールドを破棄するため、Denim のタイムスタンプを必要とするコンシューマーは、`WithOtherFields<AnyRpcHeader>` または型付きの Base レスポンスを使用してください。初期ロールアウトでは、Anvil でローカルにマイニングされたブロックが BaseTime メタデータを生成することは想定されていません。
