## Base Verify とは? {#what-is-base-verify}

Base Verify を使用すると、ユーザーは認証情報を共有することなく、[X](https://x.com/)、[Coinbase](https://www.coinbase.com/)、[Instagram](https://www.instagram.com/)、[TikTok](https://www.tiktok.com/) の認証済みアカウントを所有していることを証明できます。アプリには Sybil 耐性を確保するために利用できる決定論的なトークンが渡されます。

ウォレットのトランザクションが少なくても、Base Verify は X、Instagram、TikTok の認証済みソーシャルアカウントや [Coinbase One](https://www.coinbase.com/one) のサブスクリプションをもとに、そのユーザーが価値の高いユーザーかどうかを判別できます。これにより、オンチェーンでの活動量にかかわらず、質の高いユーザーを見極められます。

**ユースケースの例:**

* トークンゲート型のエアドロップやデイリー報酬
* 限定コンテンツへのアクセス(例: クリエイターコイン)
* ID ベースの報酬プログラムやロイヤルティプログラム

アプリでウォレット接続やメッセージ署名の実装がまだ必要な場合は、まず [ユーザーの認証](https://docs.cdp.coinbase.com/coinbase-wallet/guides/authenticate-users)、[型付きデータの署名と検証](https://docs.cdp.coinbase.com/coinbase-wallet/guides/sign-and-verify-typed-data)、または [Web React クイックスタート](https://docs.cdp.coinbase.com/coinbase-wallet/quickstart/web-react)をご覧ください。

## 基本概念 {#core-concepts}

### プロバイダー {#provider}

Base Verify が連携する ID プラットフォームです。現在、**[X](https://x.com/)**、**[Coinbase](https://www.coinbase.com/)**、**[Instagram](https://www.instagram.com/)**、**[TikTok](https://www.tiktok.com/)** に対応しています。

### 検証 {#verification}

ウォレットが特定のプロバイダーのアカウントを所有していることを示す暗号学的な証明。

### トレイト {#trait}

プロバイダーアカウントが持つ、検証可能な特定の属性です。

**例:**

* `verified: true` — X アカウントに青いチェックマークが付いている
* `coinbase_one_active: true` — Coinbase One のサブスクリプションが有効である
* `followers: gt:1000` — X アカウントのフォロワーが 1,000 人を超えている
* `followers_count: gte:5000` — Instagram アカウントのフォロワーが 5,000 人以上いる
* `video_count: gte:50` — TikTok アカウントの動画が 50 本以上ある

### アクション {#action}

ユーザーが検証を何のために使用しているかを識別する、開発者定義の文字列です。アクションを使うと、同じアプリ内でもユースケースごとに異なるトークンを発行できます。

**例:**

* `claim_daily_reward` — デイリー報酬の受け取り
* `join_allowlist` — 限定許可リストへの登録
* `unlock_premium_content` — 限定コンテンツへのアクセス
* `participate_in_raffle` — 抽選への参加

#### アクションの仕組み {#how-actions-work}

アクションは、[Sign-In with Ethereum (SIWE)](https://eips.ethereum.org/EIPS/eip-4361) メッセージの resources で指定します。

```typescript SIWE resources with action
resources: [
  'urn:verify:provider:x',
  'urn:verify:action:claim_daily_reward'
]
```

アクションは API レスポンスに含まれて返されます：

```json Verification response with action
{
  "token": "abc123...",
  "action": "claim_daily_reward",
  "wallet": "0x1234..."
}
```

#### アクションが重要な理由 {#why-actions-matter}

**アクションが異なれば、生成されるトークンも異なります。** これにより、同じ検証済みアカウントから、互いに独立した複数の請求を行えます。

* ユーザーがアクション `claim_airdrop` で X アカウントを検証 → トークン: `abc123`
* 同じ X アカウントでアクション `join_allowlist` を指定 → トークン: `def456` (異なる)
* 同じ X アカウントで再びアクション `claim_airdrop` を指定 → トークン: `abc123` (最初と同じ)

**ユースケース:**

* **複数のキャンペーン** — 互いに干渉させずに、別々のエアドロップを実施
* **機能のゲーティング** — プレミアム機能ごとに異なるトークンを使用
* **期間ごとのイベント** — イベントごとに新しいアクションを使用 (例: `raffle_jan_2025`、`raffle_feb_2025`)

#### アクション名の選び方 {#choosing-action-names}

内容がわかりやすい名前を、小文字とアンダースコアで付けてください。

| 良い例                     | 悪い例                               |
| :---------------------- | :-------------------------------- |
| `claim_genesis_airdrop` | `airdrop` (汎用的すぎる)                |
| `unlock_pro_features`   | `action1` (意味がない)                 |
| `enter_weekly_raffle`   | `base_verify_token` (予約済み／紛らわしい)  |

<Warning>
  ローンチ後はアクション名を変更しないでください。アクションを変更すると、同じユーザーに対して異なるトークンが生成されるため、Sybil 耐性が損なわれます。
</Warning>

### Token — Sybil耐性 {#token-sybil-resistance}

ウォレットではなく、プロバイダーのアカウントに紐づく決定論的な識別子です。**これがSybil攻撃対策の中核となる仕組みです。**

#### 仕組み {#how-it-works}

1. ウォレットAがXアカウントを認証 → Base Verifyが`Token: abc123`を返す → 未使用のトークンなので、エアドロップを付与します。
2. 同じXアカウントがウォレットBで再度認証を試みる → Base Verifyが`Token: abc123`を返す → 既出のトークンなので、重複請求をブロックします。

Base Verifyがなければ、ユーザーは別々のウォレットを使って何度でも請求できてしまいます。Base Verifyを使えば、1つの認証済みアカウント = 1つのトークン = 1回の請求となります。

#### トークンの特性 {#token-properties}

* **決定論的** — 同じプロバイダーアカウントからは常に同じトークンが生成されます
* **プロバイダーごとに一意** — 同じユーザーでも、X のトークンと Instagram のトークンは異なります
* **アプリごとに一意** — アプリが受け取るトークンは、他のアプリが受け取るトークンとは異なります (プライバシー保護のため)
* **アクション固有** — トークンは SIWE メッセージ内のアクションによって異なります
* **永続的** — トークンが失効したりローテーションされたりすることはありません (ユーザーが検証を削除した場合を除く)
* **特性に依存しない** — 特性が変化しても (例：フォロワー数の増加) 、トークンは変わりません

#### トークンの保存方法 {#how-to-store-tokens}

```json Verification token storage record
{
  token: "abc123...",
  walletAddress: "0x1234...",
  provider: "x",
  claimedAt: "2024-01-15",
}
```

#### 二重受け取りの防止 {#prevent-double-claims}

```typescript Prevent duplicate claims by token expandable lines
async function claimAirdrop(verificationToken: string, walletAddress: string) {
  const existingClaim = await db.findClaimByToken(verificationToken);

  if (existingClaim) {
    return { error: "This X account already claimed" };
  }

  await db.createClaim({
    token: verificationToken,
    wallet: walletAddress,
    claimedAt: new Date()
  });

  return { success: true };
}
```

### アプリ側の責務 {#your-apps-responsibilities}

* トレイト要件を含む SIWE メッセージを生成する
* ユーザーのウォレット接続を処理する
* 検証結果が見つからない場合は Base Verify App にリダイレクトする
* 再利用を防ぐため、返された検証トークンを保存する
* シークレットキーはバックエンドで安全に管理する

### Base Verify の役割 {#base-verifys-responsibilities}

* SIWE 署名を検証する
* プロバイダーでの検証情報 (X、Coinbase、Instagram、TikTok) を保存する
* 検証がトレイト要件を満たしているかを確認する
* プロバイダーとの OAuth フローを仲介する
* Sybil 耐性を確保するために決定論的なトークンを返す

### レスポンスコード {#response-codes}

| コード                                                       | 意味                                                          | 対応                                          |
| :-------------------------------------------------------- | :---------------------------------------------------------- | :------------------------------------------ |
| **200 OK**                                                | ウォレットがプロバイダーアカウントを検証済みで、かつすべてのトレイト要件を満たしています。一意のトークンが返されます。 | アクセスを許可し、トークンを保存します。                        |
| **404 Not Found**                                         | ウォレットがこのプロバイダーをまだ一度も検証していません。                               | ユーザーを Base Verify App にリダイレクトします。           |
| **400 Bad Request** (`verification_traits_not_satisfied`) | ウォレットはプロバイダーを検証済みですが、トレイト要件を満たしていません。                       | 要件を満たしていないことをユーザーに伝えます。リダイレクトは**しないでください**。 |

## はじめに {#getting-started}

### 前提条件 {#prerequisites}

1. **API キー** — [申請フォーム](https://forms.gle/6L4hWAHkojYcefz27)に記入して、アクセス権を取得してください
2. **ウォレット連携** — ユーザーがウォレットを接続し、メッセージに署名できる必要があります。[ユーザーの認証](https://docs.cdp.coinbase.com/coinbase-wallet/guides/authenticate-users) または [Web React クイックスタート](https://docs.cdp.coinbase.com/coinbase-wallet/quickstart/web-react)を参照してください
3. **バックエンドサーバー** — Base Verify API を安全に呼び出し、シークレットキーを秘匿するために必要です。フロントエンドとバックエンド間の同様の署名パターンについては、[型付きデータの署名と検証](https://docs.cdp.coinbase.com/coinbase-wallet/guides/sign-and-verify-typed-data) を参照してください

### アプリを登録する {#register-your-app}

Base Verify チームに以下の情報を提供してください:

1. **アプリのドメイン**
2. **リダイレクト URI** — 検証後にユーザーが戻るページ(例: `https://yourapp.com`)

<Warning>
  シークレットキーは**絶対に**フロントエンドのコードに含めて公開しないでください。Base Verify API の呼び出しは、必ずすべてバックエンドを経由させる必要があります。
</Warning>

## 実装 {#implementation}

<Steps>
  <Step title="アプリを設定する">
    Base Verify 連携用の設定ファイルを作成します：

    ```typescript lib/config.ts highlight={3}
    export const config = {
      appUrl: 'https://your-app.com',
      baseVerifySecretKey: process.env.BASE_VERIFY_SECRET_KEY,
      baseVerifyApiUrl: 'https://verify.base.dev/v1',
      baseVerifyMiniAppUrl: 'https://verify.base.dev',
    }
    ```

    シークレットキーを `.env.local` に追加します。

    ```shell .env.local
    BASE_VERIFY_SECRET_KEY=your_secret_key_here
    ```
  </Step>

  <Step title="SIWE署名を生成する（フロントエンド）">
    プロバイダー、トレイト要件、アクションを含む [SIWE](https://eips.ethereum.org/EIPS/eip-4361) メッセージを作成します。

    ```typescript lib/signature-generator.ts expandable lines highlight={7-12,15-24}
    import { SiweMessage, generateNonce } from 'siwe'
    import { config } from './config'

    export async function generateSignature(
      signMessageFunction: (message: string) => Promise<string>,
      address: string
    ) {
      const resources = [
        'urn:verify:provider:x',
        'urn:verify:provider:x:verified:eq:true',
        'urn:verify:provider:x:followers:gte:100',
        'urn:verify:action:claim_airdrop'
      ]

      const siweMessage = new SiweMessage({
        domain: new URL(config.appUrl).hostname,
        address,
        statement: 'Verify your X account',
        uri: config.appUrl,
        version: '1',
        chainId: 8453,
        nonce: generateNonce(),
        issuedAt: new Date().toISOString(),
        expirationTime: new Date(Date.now() + 6 * 60 * 60 * 1000).toISOString(),
        resources,
      })

      const message = siweMessage.prepareMessage()
      const signature = await signMessageFunction(message)

      return { message, signature, address }
    }
    ```
  </Step>

  <Step title="検証結果の確認 (フロントエンド → バックエンド)">
    フロントエンドで署名を生成して**自身の**バックエンドに送信し、そのバックエンドから Base Verify API を呼び出します。

    **フロントエンド:**

    ```typescript Frontend verification check expandable lines highlight={2-8,11-19}
    async function checkVerification(address: string) {
      const signature = await generateSignature(
        async (msg) => {
          return new Promise((resolve, reject) => {
            signMessage(
              { message: msg },
              { onSuccess: resolve, onError: reject }
            )
          })
        },
        address
      )

      const response = await fetch('/api/check-verification', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
        },
        body: JSON.stringify({
          signature: signature.signature,
          message: signature.message,
          address: address
        })
      })

      const data = await response.json();
      return data;
    }
    ```

    **バックエンド (自身の API エンドポイント) ：**

    ```typescript pages/api/check-verification.ts expandable lines highlight={5-8,15,19-24}
    import { validateTraits } from '../../lib/trait-validator';

    export default async function handler(req, res) {
      const { signature, message, address } = req.body;

      const expectedTraits = {
        'verified': 'true',
        'followers': 'gte:100'
      };

      const validation = validateTraits(message, 'x', expectedTraits);

      if (!validation.valid) {
        return res.status(400).json({
          error: 'Invalid trait requirements in message',
          details: validation.error
        });
      }

      const response = await fetch('https://verify.base.dev/v1/base_verify_token', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          'Authorization': `Bearer ${process.env.BASE_VERIFY_SECRET_KEY}`,
        },
        body: JSON.stringify({
          signature: signature,
          message: message,
        })
      });

      if (response.ok) {
        const data = await response.json();
        return res.status(200).json({ verified: true, token: data.token });
      } else if (response.status === 404) {
        return res.status(404).json({ verified: false, needsVerification: true });
      } else if (response.status === 400) {
        const data = await response.json();
        if (data.message === 'verification_traits_not_satisfied') {
          return res.status(400).json({ verified: false, traitsNotMet: true });
        }
      }

      return res.status(500).json({ error: 'Verification check failed' });
    }
    ```

    <Warning>
      バックエンドでは、SIWE メッセージに含まれるトレイト要件がバックエンド側の想定と一致しているかを**必ず**検証してください。これにより、ユーザーがフロントエンドでトレイト要件を改ざんし、アクセス制御を回避するのを防げます。詳しくは[セキュリティのベストプラクティス](#validate-trait-requirements)を参照してください。
    </Warning>
  </Step>

  <Step title="Base Verifyにリダイレクト（フロントエンド）">
    404 レスポンスが返された場合は、ユーザーを Base Verify App にリダイレクトし、OAuth を完了してもらいます。

    ```typescript Open the Base Verify App lines wrap expandable highlight={3-6,9}
    function redirectToVerifyMiniApp(provider: string) {
      const params = new URLSearchParams({
        redirect_uri: config.appUrl,
        providers: provider,
      })

      const miniAppUrl = `${config.baseVerifyMiniAppUrl}?${params.toString()}`

      const deepLink = `cbwallet://miniapp?url=${encodeURIComponent(miniAppUrl)}`
      window.open(deepLink, '_blank')
    }
    ```

    検証が完了すると、ユーザーは `?success=true` が付与された状態で `redirect_uri` にリダイレクトされます。再度チェック (ステップ 3) を実行すると、今度は 200 とともにトークンが返されます。Base app 向けに開発している場合は、アプリ全体の構成やライフサイクルに関するガイダンスについて [Build on Base の概要](/ja/build-on-base/overview)を参照してください。
  </Step>
</Steps>

### エラー処理 {#error-handling}

| レスポンス                                         | 対応方法                                                                |
| :-------------------------------------------- | :------------------------------------------------------------------ |
| **404**                                       | ユーザーは未認証です。Base Verify App にリダイレクトしてください。                           |
| **400** (`verification_traits_not_satisfied`) | ユーザーはアカウントを持っていますが、要件を満たしていません。メッセージを表示してください。リダイレクトや再試行は行わないでください。 |
| **200**                                       | トークンを保存し、アクセスを許可してください。                                             |

<Note>
  404 レスポンスは再試行**しないでください**。ユーザーがまだ認証を済ませていないだけです。`verification_traits_not_satisfied` を含む 400 レスポンスも再試行**しないでください**。ユーザーのアカウント指標が変化しない限り (フォロワーが増えた場合など) 、再試行しても結果は変わりません。
</Note>

## API リファレンス {#api-reference}

### 認証 {#authentication}

すべての API リクエストでは、`Authorization` ヘッダーにシークレットキーを指定する必要があります。

```http Authorization header
Authorization: Bearer YOUR_SECRET_KEY
```

### POST /v1/base_verify_token {#post-v1base_verify_token}

ウォレットに特定の検証が紐づいているかを確認し、その検証トークンを取得します。

#### リクエスト {#request}

```json POST /v1/base_verify_token request body
{
  signature: string,   // ウォレットによるSIWE署名
  message: string      // SIWEメッセージ（resources内にprovider/traitsを含む）
}
```

#### リクエスト例 {#example-request}

```bash POST /v1/base_verify_token cURL example wrap
curl -X POST https://verify.base.dev/v1/base_verify_token \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_SECRET_KEY" \
  -d '{
    "signature": "0x1234...",
    "message": "verify.base.dev wants you to sign in..."
  }'
```

#### レスポンス {#responses}

**200 OK — 検証済み：**

```json 200 OK response
{
  "token": "abc123...",
  "action": "claim_airdrop",
  "wallet": "0x1234..."
}
```

| Field    | Type   | Description                                                                     |
| :------- | :----- | :------------------------------------------------------------------------------ |
| `token`  | string | Sybil 耐性を確保するための決定論的な検証トークン。同じプロバイダーアカウントと同じアクションの組み合わせからは、常に同じトークンが生成されます。 |
| `action` | string | SIWE メッセージで指定したカスタムアクション。アクションが異なれば、生成されるトークンも異なります。                            |
| `wallet` | string | ユーザーのウォレットアドレス。                                                                 |

**404 Not Found — 検証が見つからない場合：**

```json 404 not found response
{
  "error": "verification_not_found"
}
```

ユーザーを Base Verify App にリダイレクトし、検証を完了させてください。

**400 Bad Request — トレイトの条件を満たしていません：**

```json 400 traits not satisfied response
{
  "code": 9,
  "message": "verification_traits_not_satisfied",
  "details": []
}
```

ユーザーはプロバイダーアカウントを保有していますが、トレイトの要件を満たしていません。リダイレクトは行わないでください。

**401 Unauthorized — 無効なキー:**

```json 401 unauthorized response
{
  "error": "unauthorized"
}
```

シークレットキーが正しいこと、およびAuthorizationヘッダーに含まれていることを確認してください。

```text Base Verify redirect URL format
https://verify.base.dev?redirect_uri={your_app_url}&providers={provider}
```

| パラメーター         | 必須 | 説明               | 例                                      |
| :------------- | :- | :--------------- | :------------------------------------- |
| `redirect_uri` | はい | 検証後のユーザーのリダイレクト先 | `https://yourapp.com`                  |
| `providers`    | はい | 検証対象のプロバイダー      | `x`, `coinbase`, `instagram`, `tiktok` |

## トレイトカタログ {#trait-catalog}

トレイトとは、検証可能なプロバイダーアカウント固有の属性です。トレイトは、[SIWE](https://eips.ethereum.org/EIPS/eip-4361) メッセージの resources 内で次の形式で指定します。

```text Trait resource format
urn:verify:provider:{provider}:{trait_name}:{operation}:{value}
```

### 演算子 {#operations}

| 演算子            | 記号    | 適用対象  | 説明                     | 例                                  |
| :------------- | :---- | :---- | :--------------------- | :--------------------------------- |
| 等しい            | `eq`  | すべての型 | 完全一致                   | `verified:eq:true`                 |
| より大きい          | `gt`  | 整数    | 指定値より大きい (指定値を含まない)    | `followers:gt:1000`                |
| 以上             | `gte` | 整数    | 指定値以上                  | `followers:gte:1000`               |
| より小さい          | `lt`  | 整数    | 指定値より小さい (指定値を含まない)    | `followers:lt:5000`                |
| 以下             | `lte` | 整数    | 指定値以下                  | `followers:lte:5000`               |
| いずれかに一致 (リスト)  | `in`  | 文字列   | 値がカンマ区切りのリストのいずれかに一致する | `verified_type:in:blue,government` |

### 型システム {#type-system}

**ブール型トレイト:**

* 値: `"true"` または `"false"` (文字列として指定)
* `eq` 演算のみサポート
* 例: `verified:eq:true`

**整数型トレイト:**

* 値: 数値 (文字列として指定)
* サポートする演算: `eq`、`gt`、`gte`、`lt`、`lte`
* 例: `followers:gte:1000`

**文字列型トレイト:**

* 値: テキスト文字列
* サポートする演算: `eq`、`in`
* 例: `verified_type:eq:blue` または `verified_type:in:blue,government`

### トレイトの組み合わせ {#combining-traits}

同じプロバイダーに複数のトレイトを指定した場合は、そのトレイトが**すべて**満たされている必要があります (AND 条件) 。

```typescript Multiple traits for one provider
resources: [
  'urn:verify:provider:x',
  'urn:verify:provider:x:verified:eq:true',
  'urn:verify:provider:x:followers:gte:10000'
]
```

<Note>
  1 回のリクエストで確認できるプロバイダーは 1 つだけです。複数のプロバイダーを確認する場合は、プロバイダーごとに API を呼び出してください。
</Note>

### よく使われるパターン {#common-patterns}

**段階的なアクセス制御：**

```typescript Tiered access trait rules lines wrap expandable
// ブロンズティア: 認証済みアカウントすべて
traits: { 'verified': 'true' }

// シルバーティア: フォロワー1,000人以上
traits: { 'followers': 'gte:1000' }

// ゴールドティア: フォロワー10,000人以上
traits: { 'followers': 'gte:10000' }
```

## セキュリティとプライバシー {#security-and-privacy}

### SIWE署名の要件 {#siwe-signature-requirement}

すべてのAPI呼び出しには、ウォレット所有者による有効な[SIWE](https://eips.ethereum.org/EIPS/eip-4361)署名が必要です。これにより、以下を防止します。

* 検証ステータスの無差別な照会
* 第三者によるウォレットの検証状況の確認
* 列挙攻撃

ユーザーは構造化メッセージに署名し、自身がウォレットを管理していること、および特定のトレイトの確認に同意していることを証明します。

```json SIWE payload example lines wrap expandable
{
  domain: "your-app.com",
  address: "0x1234...",
  chainId: 8453,
  resources: [
    "urn:verify:provider:x",
    "urn:verify:provider:x:verified:eq:true",
    "urn:verify:action:claim_airdrop"
  ]
}
```

### トレイト要件を検証する {#validate-trait-requirements}

<Warning>
  バックエンドがフロントエンドから SIWE メッセージを受け取ったら、メッセージ内のトレイト要件がバックエンドの想定と一致していることを**必ず**検証してください。これにより、ユーザーがフロントエンド側でトレイト要件を改ざんしてアクセス制御を回避するのを防げます。
</Warning>

**検証を行わない場合の攻撃例:**

1. アプリがユーザーにフォロワー 100 人以上を要件として課している
2. ユーザーがフロントエンドを改ざんし、フォロワー 10 人のみを要求するよう変更する
3. ユーザーが改ざんしたメッセージに署名する
4. 検証がないため、バックエンドはそのリクエストを Base Verify にそのまま転送してしまう
5. ユーザーはフォロワーが 100 人未満であるにもかかわらずアクセス権を得てしまう

**実装:**

```typescript Validate traits on the backend lines wrap expandable highlight={2-4,7}
import { validateTraits } from './lib/trait-validator';

const expectedTraits = {
  'followers': 'gte:100'
};

const validation = validateTraits(message, 'x', expectedTraits);

if (!validation.valid) {
  return res.status(400).json({
    error: 'Invalid trait requirements in message',
    details: validation.error
  });
}
```

### シークレットキーを保護する {#protect-your-secret-key}

**絶対にしてはいけないこと:**

* フロントエンドのコードにシークレットキーを含める
* `NEXT_PUBLIC_*` など、ブラウザに公開される環境変数を使用する
* シークレットキーをバージョン管理システムにコミットする
* チャット、メール、ドキュメントでシークレットキーを共有する

**必ず行うこと:**

* シークレットキーはバックエンドの環境変数にのみ保存する
* gitignore に登録した `.env` ファイルを使用する
* 誤って漏洩した場合は、直ちにキーをローテーションする
* Base Verify API はバックエンドからのみ呼び出す

### OAuth のセキュリティモデル {#oauth-security-model}

Base Verify は、[OAuth](https://oauth.net/2/) を使用してプロバイダーのアカウントを検証します。

1. ユーザーが Base Verify App で OAuth を開始します
2. プロバイダー (X、Instagram など) がユーザーを認証します
3. プロバイダーが Base Verify に OAuth トークンを返します
4. Base Verify が OAuth トークンを使用してアカウントデータを取得します
5. Base Verify が検証結果をユーザーのウォレットに紐づけて保存します
6. OAuth トークンは暗号化され、安全に保存されます

アプリ側で OAuth トークンやリダイレクトを扱う必要はありません。これらはすべて Base Verify App 内で処理されます。

### データの保存 {#data-storage}

**Base Verify が保存するデータ:**

* 認証済みプロバイダーアカウントに紐づくウォレットアドレス
* プロバイダーアカウントのメタデータ (ユーザー名、フォロワー数、認証ステータス)
* OAuth トークン (暗号化して保存され、アプリと共有されることはありません)
* 認証のタイムスタンプ

**Base Verify が保存しないデータ:**

* ユーザーの秘密鍵
* プロバイダーアカウントのパスワード
* ユーザーのアクティビティや閲覧履歴
* 認証に必要な範囲を超えるデータ全般

**アプリが受け取るデータ:**

`/v1/base_verify_token` を呼び出した際に返されるのは、`token`、`action`、`wallet` のみです。個人を特定できる情報 (PII) は一切返されません。

### ユーザーによる管理 {#user-control}

ユーザーは自身の検証情報をいつでも削除できます。削除すると、次のようになります。

* 保存されているプロバイダーデータがすべて削除されます
* 以降、トークンは生成できなくなります
* アプリに保存されているトークンは無意味になります (ユーザーは同じアカウントで再検証できません)

### キャッシュ {#caching}

API 呼び出しを減らすため、検証結果をキャッシュします。

* キャッシュはユーザーのセッション中のみ保持する (永続的に保存しない)
* ユーザーがウォレットを切断したらキャッシュを消去する
* ページを読み込むたびに検証状況を確認しない
