本指南汇总了使用官方 [Base Node Docker 配置](https://github.com/base/base)搭建和运行 Base 节点时的常见问题，并提供相应的诊断与解决步骤。

## 常规故障排除步骤 {#general-troubleshooting-steps}

在排查具体问题之前，可以先尝试以下几个通常有效的常规步骤：

1. **检查容器日志**：这通常是最能提供有用信息的一步。使用 `docker compose logs -f <service_name>` 查看特定容器的实时日志。
   * L2 客户端 (Reth) ：`docker compose logs -f execution`
   * Rollup 节点：`docker compose logs -f node`。留意其中的错误、警告或反复出现的消息。

2. **检查容器状态**：使用 `docker compose ps` 确认相关 Docker 容器是否正在运行。如果某个容器频繁重启或已退出，请查看其日志。

3. **检查资源使用情况**：监控服务器的 CPU、内存、磁盘 I/O 和网络使用情况。性能问题往往与资源不足有关。可以借助 `htop`、`iostat` 和 `iftop` 等工具进行排查。

4. **验证 RPC 端点**：使用 `curl` 检查 L2 客户端的 RPC 端点是否有响应 (参见[运行节点](/zh/specifications/node-operators/run-a-node#running-a-node)) 。同时，确认 L1 端点配置正确，且可以从节点服务器访问。

5. **检查 L1 节点**：确保所配置的 L1 节点 (执行层和共识层) 已完全同步、运行正常且可以访问。L1 节点出现问题会导致 L2 节点无法正常同步。

## 常见问题与解决方案 {#common-issues-and-solutions}

### 安装与配置问题 {#setup-configuration-issues}

* **问题**：Docker 命令执行失败 (`docker compose up ...`)
  * **检查**：是否已安装 Docker 和 Docker Compose，且 Docker 守护进程正在运行？
  * **检查**：当前是否位于正确的目录 (即克隆得到的、包含 `docker-compose.yml` 的 `base/base` 目录) ？
  * **检查**：命令中是否存在语法错误 (例如 `NETWORK_ENV` 拼写错误) 。

* **问题**：容器无法启动，日志中出现与 `.env` 文件或环境变量相关的错误。
  * **检查**：是否已在正确的 `.env` 文件 (`.env.mainnet` 或 `.env.sepolia`) 中正确配置 L1 端点 (`BASE_NODE_L1_ETH_RPC`、`BASE_NODE_L1_BEACON`) ？
  * **检查**：`.env` 文件中的 `RETH_CHAIN` 和 `RETH_SEQUENCER_HTTP` 是否已正确设置？

* **问题**：出现与 JWT 密钥相关的错误，或 `base-consensus` 与执行客户端之间的身份验证错误。
  * **检查**：除非你清楚自己在做什么，否则请勿手动修改 `BASE_NODE_L2_ENGINE_AUTH` 变量或 JWT 文件路径 (`$BASE_NODE_L2_ENGINE_AUTH`) 。`docker-compose` 配置通常会自动处理这些设置。

* **问题**：出现与数据卷 (`./reth-data`) 相关的权限错误。
  * **检查**：确保运行 `docker compose` 的用户对 `base/base` 仓库的克隆目录 (或你配置的 `HOST_DATA_DIR`) 拥有写入权限。Docker 需要能够写入 `./reth-data`。使用 `sudo` 运行 Docker 命令有时会导致后续出现权限问题；建议改用已加入 `docker` 用户组的非 root 用户运行。

### 同步问题 {#syncing-problems}

* **问题**：节点未开始同步或似乎卡住 (区块高度不再增长) 。
  * **检查**：`base-consensus` 日志。排查连接 L1 端点或执行客户端时出现的错误。
  * **检查**：执行客户端的日志。排查通过 Engine API (端口 `8551`) 连接 `base-consensus` 时出现的错误或 P2P 问题。
  * **检查**：L1 节点的健康状况和同步状态。L1 节点是否可以访问且已完全同步？
  * **检查**：系统时间。确保服务器时钟已准确同步 (使用 `ntp` 或 `chrony`) 。时间偏差过大可能导致 P2P 问题。

* **问题**：同步速度极慢。
  * **检查**：硬件规格。是否满足[节点性能](/zh/specifications/node-operators/performance-tuning)指南中列出的推荐配置 (尤其是 RAM 和 **NVMe SSD**) ？磁盘 I/O 往往是瓶颈所在。
  * **检查**：L1 节点性能。你的 L1 RPC 端点响应是否及时？L1 节点响应缓慢会拖慢 L2 同步。
  * **检查**：网络连接质量和带宽。
  * **检查**：`base-consensus` 和执行客户端日志中是否有性能警告或错误。

* **问题**：`optimism_syncStatus` (`base-consensus` 的端口 `7545`) 显示较大的时间差或报错。
  * **操作**：查看查询状态前后这段时间内 rollup 节点和 L2 执行客户端的日志，找出根本原因 (例如 L1 连接问题、L2 客户端问题) 。

* **问题**：发送交易时出现 `Error: nonce has already been used`。
  * **原因**：节点尚未完全同步到链头。
  * **操作**：等待节点完全同步。可通过 `optimism_syncStatus` 或日志监控同步进度。

### 性能问题 {#performance-issues}

* **问题**：CPU、内存或磁盘 I/O 占用过高。
  * **检查**：对照[节点性能](/zh/specifications/node-operators/performance-tuning)中的建议核查硬件规格，必要时进行升级。务必使用本地 NVMe SSD。
  * **检查**：查看客户端日志，排查具体错误或性能瓶颈。

### 快照恢复问题 {#snapshot-restoration-problems}

正确的操作步骤请参阅[快照](/zh/specifications/node-operators/snapshots)指南。

* **问题**：`wget` 命令执行失败，或下载的快照文件已损坏。
  * **检查**：网络连接。
  * **检查**：可用磁盘空间。
  * **操作**：重新下载，并确认下载 URL 正确无误。

* **问题**：`tar` 解压失败。
  * **检查**：下载文件的完整性 (文件是否已损坏？) 。
  * **检查**：可用磁盘空间 (解压所需空间远大于下载文件本身) 。
  * **检查**：`tar` 命令语法。

* **问题**：恢复快照后节点无法启动，日志显示数据库错误或文件缺失。
  * **检查**：是否在修改数据目录*之前*停止了节点 (`docker compose down`) ？
  * **检查**：在解压/移动快照数据之前，是否已删除旧数据目录中的*内容* (`./reth-data/*`) ？
  * **检查**：快照数据是否移动到了正确位置？链数据需要直接位于 `./reth-data` 下，而不是嵌套在子文件夹中 (例如 `./reth-data/reth/...`) 。请核实文件夹结构。

* **问题**：下载或解压过程中磁盘空间不足。
  * **操作**：释放磁盘空间，或配置更大的存储卷。请牢记存储空间计算公式：
    ```
    (2 * chain_size + snapshot_size + 20% buffer)  
    ```

### 网络/连接问题 {#networking-connectivity-issues}

* **问题**：RPC/WS 连接被拒绝 (例如，使用 `curl` 访问 `localhost:8545` 失败) 。
  * **检查**：L2 客户端容器是否正在运行 (`docker compose ps`) ？
  * **检查**：是否使用了正确的端口 (默认 HTTP 为 `8545`，WS 为 `8546`) ？
  * **检查**：L2 客户端日志。RPC 服务器是否启动失败？
  * **检查**：客户端配置/入口点中的 `--http.addr` 和 `--ws.addr` 标志是否设置为 `0.0.0.0`，以允许外部连接 (在 Docker 网络内) ？

* **问题**：节点的对等节点数量过少，或无法连接到任何对等节点。
  * **检查**：防火墙是否已开放入站端口 `30303` (TCP/UDP) 和 `9222` (TCP/UDP，用于 Reth discv5) 。
  * **检查**：出站端口 `30301` (TCP/UDP) 和 `9200` (UDP) 是否已放行出站流量。节点需要通过这些端口连接 Base 引导节点——如果访问这些端口的出站连接被阻止，无论入站规则如何配置，节点都无法发起对等节点发现，也就找不到任何对等节点。
  * **检查**：节点日志中是否有 P2P 错误。
  * **操作**：如果节点位于 NAT 之后，请通过 `.env` 文件中的 `ADDITIONAL_ARGS` 配置 `--nat=extip:<your-ip>` 标志 (参见[网络](/zh/specifications/node-operators/run-a-node#networking)) 。

* **问题**：日志中报告端口冲突，或 `docker compose up` 失败。
  * **检查**：主机上是否有其他服务占用了默认端口 (`8545`、`8546`、`8551`、`6060`、`7545`、`30303`) ？可使用以下命令排查：
    ```bash
    sudo lsof -i -P -n | grep LISTEN
    sudo netstat -tulpn | grep LISTEN
    ```
  * **操作**：停止冲突的服务，或修改 `docker-compose.yml` 中的 `ports` 部分，更改 Base 节点容器使用的端口；如有必要，还需同步更新 `.env` 文件中的相关环境变量 (`$RPC_PORT`、`$WS_PORT` 等) 。
