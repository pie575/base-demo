## 摘要 {#summary}

Holocene 硬分叉对区块派生规则做了若干变更，使派生管道总体上更严格、更简洁，并改善了故障证明 (Fault Proofs) 和互操作 (Interop) 的最坏情况。具体变更如下：

* *严格批次排序 (Strict Batch Ordering)&#x20;*&#x20;要求通道内及跨通道的批次严格有序。
* *部分跨度批次有效性 (Partial Span Batch Validity)&#x20;*&#x20;对跨度批次中的各个单一批次分别判定有效性，仅在遇到第一个无效单一批次时，才使跨度批次的剩余部分失效。
* *快速通道失效 (Fast Channel Invalidation)&#x20;*&#x20;相当于将部分跨度批次有效性应用于通道层：一旦发现无效批次，即令该通道的后续部分失效。
* *稳定区块派生 (Steady Block Derivation)&#x20;*&#x20;会将无效的载荷属性立即派生为仅包含存款的区块。

这些变更的综合效果是：无效批次的影响仅限于当前区块号，而不会在安全链中向前或向后传播；同时，引擎阶段的无效载荷也被限制在引擎内部，不会在派生管道中向后传播。

为实现上述目标，Holocene 派生对派生管道做了以下变更。

## 帧队列 (Frame Queue) {#frame-queue}

帧队列的功能保持不变，用于缓存最近一笔 (或多笔) 批处理交易中尚未组装成通道的所有帧。Holocene 仍然允许每笔批处理交易包含多个帧，且这些帧可能来自不同的通道。与之前一样，批处理交易的剩余空间可以选择用下一个通道的起始帧来填充。

然而，严格批次排序 (Strict Batch Ordering) 为帧队列引入了以下额外的检查和规则：

* 如果从批处理交易中解码出的&#95;非首帧&#95; (即索引 &gt;0 的帧) 是&#95;乱序&#95;的，则会被**立即丢弃**。满足以下任一条件的帧即视为&#95;乱序&#95;：
  * 其通道 ID 与前一帧相同，但帧编号不等于前一帧的编号加一；或
  * 前一帧已经关闭了具有相同 ID 的通道；或
  * 该非首帧的通道 ID 与帧队列中前一帧的通道 ID 不同。
* 如果解码出一个&#95;首帧&#95;时，前一帧不是&#95;末帧&#95; (即 `is_last` 为
  `false`) ，则同一通道的所有先前帧都会被丢弃，而这个新的首帧保留在队列中。

这些规则保证了对每个通道而言，帧队列中保存的帧始终按索引有序、连续且包含首帧。此外，一个通道的首帧要么是队列中的第一帧，要么紧跟在上一个通道的关闭帧之后。

请注意，这些规则与 Holocene 之前的规则不同：在 Holocene 之前，乱序帧会被缓存，帧有效性检查仅在通道库 (Channel Bank) 阶段进行。将这些检查提前到帧队列阶段执行，可以更快地丢弃无效帧，从而降低各类实现的内存占用。

## 通道库 {#channel-bank}

由于通道帧必须按顺序到达，通道库 因此大为简化，
同一时间最多只保存一个通道。

### 修剪 {#pruning}

由于通道库 (channel bank) 中最多只有一个打开的通道，修剪过程大为简化。
通道库的队列实际上变成了单个通道的暂存槽位，该通道称为 *暂存通道* (staging channel) 。
`MAX_CHANNEL_BANK_SIZE` 参数不再使用，同时要求暂存通道压缩后的大小
不超过 `MAX_RLP_BYTES_PER_CHANNEL` (否则丢弃该通道) 。请注意，现有规则规定，任何给定通道的 *未压缩* 大小会在[解压期间](/zh/specifications/base-protocol/consensus/derivation#channel-format)被 *截断* 至 `MAX_RLP_BYTES_PER_CHANNEL`；
而后一条规则与之相比，触发条件和产生的效果均不相同。

### 超时 {#timeout}

超时的处理方式与之前相同，只是现在仅作用于单个暂存通道 (staging channel) 。

### 读取与帧加载 {#reading-frame-loading}

帧队列保证每个通道内的帧都是有序且连续的。因此，通道库中的读取和
帧加载变得更加简单：

* 新通道的第一帧会开启一个新通道，并将其作为暂存通道。
  * 如果已存在一个处于打开状态且尚未完成的暂存通道，则丢弃该通道，并以这个
    新通道取而代之。这与帧队列的行为一致：当新通道的第一帧到达时，帧队列会丢弃
    所有未关闭通道的帧。
* 如果当前通道已超时但尚未被修剪，且传入的帧恰好是该通道的下一个
  正确帧，则丢弃该帧和该通道，连同帧队列中可能仍残留的该通道所有后续帧。
  请注意，Holocene 之前就已存在等效规则。
* 向暂存通道添加一帧后，如果该通道的原始压缩大小 (按 Bedrock 规范定义)
  超过 `MAX_RLP_BYTES_PER_CHANNEL`，则丢弃该通道。此规则取代了
  Holocene 之前由 `MAX_CHANNEL_BANK_SIZE` 规定的所有通道合计大小上限。

## 跨度批次 {#span-batches}

部分 跨度批次 有效性 (Partial 跨度批次 Validity) 改变了 [跨度批次](../delta/span-batches) 的原子有效性模型。
在 Holocene 中，跨度批次 被视为派生管道中位于批次队列之前的一个可选阶段，
批次队列从这个前置的 跨度批次 阶段拉取单一批次 (singular batch) 。遇到无效的单一批次时，该批次会被丢弃；
出于一致性考虑，跨度批次 的剩余部分也会一并丢弃。我们称之为 *前向失效 (forwards-invalidation)&#x20;*。不过，与 Holocene 之前不同，
我们不会对来自同一 跨度批次 的先前有效批次进行 *后向失效 (backwards-invalidate)&#x20;*。

如果从当前暂存通道派生出的批次是单一批次，则直接将其转发
到批次队列；否则，将其设为 跨度批次 阶段中的当前 跨度批次。在从中派生单一批次之前，
需执行以下 跨度批次 有效性检查。
相关定义沿用 [原始 跨度批次 规范](../delta/span-batches)。

* 如果 跨度批次 的 *L1 origin 检查* 不属于规范 L1 链，则该 跨度批次
  无效。
* 父级检查失败会使 跨度批次 无效。
* 如果 `span_start.timestamp > next_timestamp`，则该 跨度批次 无效，因为新的严格批次排序规则
  不允许存在间隙。
* 如果 `span_end.timestamp < next_timestamp`，则该 跨度批次 的有效性被设为 `past`，因为它
  不包含任何新批次 (若对每个派生出的单一批次分别进行时间戳检查，结果也是如此) 。有关新增的
  `past` 有效性，请参阅下文 [Batch Queue](#batch-queue) 部分。
* 注意，我们仍然允许 跨度批次 与安全链重叠 (`span_start.timestamp <
  next_timestamp`) 。

如果上述任一检查使 跨度批次 无效，则该 跨度批次 会被 `drop`，派生出该 跨度批次 的
剩余通道也会立即被丢弃 (另请参阅 [快速通道
失效](#fast-channel-invalidation)) 。但对于 `past` 跨度批次，只丢弃该 跨度批次 本身，
而不丢弃剩余通道。

> [!Note]
> 关于重叠的 跨度批次，需要补充说明一点：现有的批次队列规则中已有一条规则，
> 即丢弃 L1 origin 早于 L2 安全头 (safe head) 的 L1 origin 的批次。Delta 跨度批次
> 检查中也有一条等效规则，适用于安全头之后的所有单一批次。
> 虽然 Holocene 不再执行完整的 跨度批次 检查，但批次队列规则仍然
> 适用于从 跨度批次 中流式输出的单一批次，因此，这条规则尤其仍然
> 适用于来自重叠 跨度批次、位于当前安全头之后的第一个单一批次。
>
> 这是实现中一个已知的易错点：只有在从 跨度批次 中提取出完整的单一批次数组
> 并填充其 L1 origin 哈希之后，才能最早检测到违反此规则的情况。因此，务必将 L1 origin 编号过时
> 或因其他原因无效的单一批次视为无效，并据此将该 跨度批次 视为无效，
> 而不应产生导致派生停滞的严重派生错误。

## 批次队列 (Batch Queue) {#batch-queue}

批次队列同样得到了简化：批次必须严格按顺序到达，任何违反排序要求的批次都会被立即丢弃，而不再进行缓冲。

因此，对 [Bedrock 批次队列](/zh/specifications/base-protocol/consensus/derivation#batch-queue)做出以下更改：

* 移除重排序步骤，由后续检查丢弃不连续的批次。
* 移除 `future` 批次有效性状态，原先被判定为未来批次的批次现在会被直接 `drop` (丢弃) 。这实际上禁止了间隙的出现，不再缓冲未来批次。
* 引入新的批次有效性 `past`。如果批次的时间戳早于或等于安全头 (safe head) 的时间戳，则该批次具有 `past` 有效性。这同样适用于跨度批次 (span batch) 。
* 其他规则保持不变，包括在排序窗口 (sequencing window) 结束时生成空批次。

请注意，这些批次有效性规则的更改同样依据批次被包含的 L1 区块的时间戳激活，而非依据批次时间戳。这对于确保 Holocene 激活后第一个通道的验证规则保持一致至关重要。

`drop` 和 `past` 批次有效性会带来以下新行为：

* 如果某个批次被判定为无效并被丢弃，则其所属跨度批次 (如适用) 的剩余部分也会被丢弃。
* 如果某个批次被判定为 `past` 批次，则会被静默丢弃，其所属跨度批次的剩余部分继续处理。这同时适用于跨度批次和单一批次。

请注意，当批次队列的 L1 起源向前推进时，可以保证队列为空，因为未来批次不再被缓冲。此外，由于未来批次会被直接丢弃，批次队列实际上变成了一个更简单的&#95;批次阶段&#95;：它最多持有一个跨度批次并从中读取单一批次，自身不再使用队列缓冲单一批次。有效批次会被直接转发到下一阶段。

### 快速通道失效 {#fast-channel-invalidation}

此外，一旦发现无效批次，派生出该批次的通道中的剩余部分也会被丢弃。

## Engine Queue {#engine-queue}

如果引擎对常规派生的载荷返回 `INVALID` 状态，则该载荷将被替换为另一个载荷：除 `transaction_list` 被裁剪为仅保留其中的存款交易外，其余字段均保持不变。

与之前一样，如果随后仍无法处理这些仅含存款交易的属性，则视为严重错误。

如果无效载荷被替换为仅含存款交易的载荷，出于一致性考虑，该载荷所源自的剩余 跨度批次 (如适用) 以及 channel 也将一并丢弃。

## 属性构建器 {#attributes-builder}

从分叉激活区块之后开始，属性构建器生成的 `PayloadAttributes` 将包含
[执行引擎规范](./exec-engine#eip-1559-parameters-in-payloadattributesv3)中描述的 `eip1559Params` 字段。该
值存储在 `SystemConfig` 中。

在分叉激活区块上，属性构建器将包含一个全零的 `eip1559Params`，以指示
引擎使用 [Canyon 基础费用参数常量](/zh/specifications/base-protocol/execution/l2-execution-engine#1559-parameters)。这样
做是为了用默认的 EIP-1559 参数值初始化流水线所见的 `SystemConfig` 状态。在第一个
Holocene 载荷处理完毕后，后续载荷应使用 `SystemConfig` 中的 EIP-1559 分母和弹性
参数作为 `eip1559Params` 字段的值。当流水线遇到 `UpdateType.EIP_1559_PARAMS`
类型的 `ConfigUpdate` 事件时，流水线的系统配置将与 `SystemConfig` 合约中的配置保持同步。

## 激活 {#activation}

当 *L1 包含区块时间戳* 大于或等于 Holocene 激活时间戳时，新的批次规则即生效。请注意，这与 跨度批次 在
[Delta](../delta/overview) 中的激活方式不同，后者依据的是 跨度批次 的 L1 origin 时间戳。

当派生管道的 L1 遍历阶段将其 origin 推进到首个时间戳大于或等于 Holocene 激活时间戳的 L1 区块时，
派生管道的状态将基本重置，具体做法是**丢弃**：

* 帧队列中的所有帧，
* 通道库中的通道，以及
* 批次队列中的所有批次。

随后，这三个阶段将由新的 Holocene 帧队列、通道库和批次队列取代
(根据具体实现，还可能添加可选的 跨度批次 阶段) 。

请注意，batcher 实现必须了解这一激活行为：对于部分提交的通道，凡是在 Holocene 之前已被包含的帧都必须重新发送。
不过这种情况极少发生，因为生产环境中的 batcher 通常配置为在单笔交易中提交整个通道。

## 设计依据 {#rationale}

### 严格的帧与批次排序 {#strict-frame-and-batch-ordering}

严格的帧与批次排序 (Strict Frame and Batch Ordering) 简化了派生管道的实现，并改善了最坏情况下的缓存数据用量。

* 帧队列 (frame queue) 始终只保存来自单笔 batcher 交易的帧。
* 通道库 (channel bank) 始终只保存一个暂存通道，该通道要么正由传入的帧逐步构建，要么正由后续阶段处理。
* 批次队列 (batch queue) 最多只保存一个 (正在处理的) 跨度批次 (span batch) 和一个单一批次 (singular batch)  (来自该跨度批次，或直接来自暂存通道)
* 在一般的生产场景中，同步启动 (sync start) 过程大为简化。

这对故障证明 (Fault Proof) 程序的实现十分有利。

### 部分 跨度批次 有效性 {#partial-span-batch-validity}

部分 跨度批次 有效性保证：从 跨度批次 派生出的有效单一批次 (singular batch) 可以
立即作为有效批次处理并推进安全链，而不必在整个 跨度批次 全部转换为单一批次之前一直处于未决状态。
这使派生速度更快，并为故障证明 (Fault Proofs) 提供了强有力的最坏情况保证，因为区块的有效性
不再依赖于任何后续区块的有效性。请注意，在 Holocene 之前，要验证 跨度批次 的第一个区块，
必须先验证整个 跨度批次。

### 快速通道失效 {#fast-channel-invalidation-2}

新的快速通道失效 (Fast Channel Invalidation) 规则是严格排序规则 (Strict Ordering Rules) 在一致性上的必然推论。
由于通道内的批次必须有序且连续，假设通道内的所有批次彼此自洽 (即父 L2 哈希指向由前一个
批次产生的区块) ，那么一旦出现无效批次，同一通道中其后的所有剩余批次也会随之失效。

### 稳定区块派生 (Steady Block Derivation) {#steady-block-derivation}

稳定区块派生 (Steady Block Derivation) 修改了无效载荷属性 (payload attributes) 的派生规则，会将无效载荷替换为仅含存款交易的载荷或空载荷。
关键在于，这样一来，无效载荷的影响就不会在派生管道中向后传播。这对故障证明 (Fault Proofs)
和互操作 (Interop) 都有好处：它保证批次的有效性不受后续阶段影响，并且在引擎阶段从上一阶段拉取新的载荷属性之前，
由有效批次派生出的区块就已由引擎阶段确定。这样可以避免规模更大的派生管道重置。

### 防御性更低的协议 {#less-defensive-protocol}

更严格的派生规则让协议无需再那么&quot;防御&quot;。旧的协议规则允许为无效载荷提供第二次机会，也允许在通道内乱序提交帧和批次。
Base 一年半以上的运行经验表明，这些宽松的
派生规则 (几乎) 从未派上用场。因此，更可取的做法是采用更严格的规则，以改善故障证明 (Fault Proofs) 和互操作 (Interop) 的最坏情况。

此外，较宽松的规则会带来更多边界情况和复杂的交互，
使协议更难以分析和测试，从而增加了
不同实现之间出现链分叉的风险。

## 安全与实现注意事项 {#security-and-implementation-considerations}

### 重组 (Reorgs) {#reorgs}

在引入 Steady Block Derivation 之前，无效的 载荷 仍有机会被后续有效的
载荷 替换。而现在它们会立即被替换为仅含存款 (deposit-only) 的 载荷，因此
理论上发生 unsafe 链重组的风险有所上升。据我们所知，Base 目前尚未
出现过这种情况。

*有效* 批次导致 *无效* 载荷 的场景只可能有以下两种：

* sequencer+batcher 存在缺陷或具有恶意
* 未来，该 载荷 中引用的某个原本有效的 Interop 依赖后来
  被判定为无效，而包含该 Interop 依赖的区块已被打包进批次。

Steady Block Derivation 规则正是针对后一种情况而设计的。该规则确保
无效 Interop 依赖的次生影响仅局限于单个区块，从而
避免引发跨 L2 的 Interop 连锁重组，导致 L2 链被反复回溯。

### Batcher 加固 {#batcher-hardening}

从某种意义上说，Holocene 将部分复杂性从推导阶段转移到了批处理阶段。推导规则更简单、
更严格，相应地就需要更复杂的 batcher 实现来满足。

batcher 必须经过加固，以确保满足严格的排序要求。当前的 Go 实现在实践中已基本
满足这些要求，但更多是出于巧合而非刻意设计。在某些边缘情况下，batcher 仍可能违反严格的排序规则。例如，如果某个 channel
未能在设定时间内完成提交，相应的区块会被重新排队，从而可能导致批次乱序。此外，在区块被重新排队、
而后续 channel 已在 mempool 中等待打包的场景下，batcher 实现还需格外注意，确保动态切换 blob/calldata
不会导致批次乱序或出现空缺。

建议 batcher 实现在第一笔 batcher 交易 (在当前生产环境的 batcher 配置下，这几乎总是某个 channel 唯一的一笔 batcher 交易) 开始提交后，
固定 nonce 与区块范围之间的对应关系。这样应能避免批次乱序或出现
空缺。为此，可能需要在交易管理中实现某种形式的持久化，因为无法可靠地恢复 L1 网络中所有全局处于 pending 状态的
batcher 交易。

此外，batcher 实现需要了解 Steady Block Derivation 规则，
即无效的 载荷 将被推导为仅含存款 (deposit-only) 的区块。因此，一旦发生 unsafe 重组，
batcher 应等待 sequencer 从 L1 推导出所有区块，确保只在重组后的链段 (其中可能包含推导出的仅含存款区块) 之上
开始批处理新区块。batcher 应反复查询
sync-status，并将其与预期的 safe 链进行比对。一旦发现任何
不一致，batcher 应停止批处理，等待 sequencer 完整推导至
最新的 L1 batcher 交易后，再继续批处理。

### 同步起点 {#sync-start}

得益于新的严格帧与批次排序规则，同步起点算法在一般情况下可以得到简化。这些规则保证：

* 新通道的首帧到达时，帧队列和通道库中先前未关闭通道的未完成帧会被丢弃；并且
* 当派生管道的 L1 源头向前推进时，批次队列为空。

因此，同步起点算法可以乐观地从引擎中选取最新的 L2 unsafe、safe 和 finalized 头；如果 L2 safe 头的 L1 源头是&#95;合理的&#95; (详见
[原始同步起点说明](/zh/specifications/base-protocol/consensus/derivation#finding-the-sync-starting-point)) ，
则从该 L1 源头开始推导。

* 如果找到的第一个帧是包含 safe 头的通道的&#95;首帧&#95; (待定：甚至
  只需是以当前 safe 头为父块的下一个 L2 区块) ，就可以
  安全地从该通道继续推导，因为先前的派生管道状态不可能
  影响到 L2 safe 头。
* 如果找到的第一个帧不是首帧，则需要回溯一个完整的通道
  超时窗口，查看能否找到该通道的起始帧。
  * 如果找到了起始帧，就可以从该帧继续推导。
  * 如果没有找到起始帧，则需要回退到 finalized L2 头的 L1 源头之前
    一个完整的通道超时窗口处。

关于最后一种情况需要注意：如果在一个通道超时窗口内未找到起始帧，
那么已找到的帧所属的通道必然已经超时，并会被丢弃。我们要寻找的 safe 区块不可能位于任何在其 L1 源头之前就已超时的通道中，因此无需
再往前搜索，只需回退到 finalized L2 头之前一个通道超时窗口处即可。
