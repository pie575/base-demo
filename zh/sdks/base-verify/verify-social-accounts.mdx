## 什么是 Base Verify？ {#what-is-base-verify}

借助 Base Verify，用户无需共享凭据，即可证明自己拥有 [X](https://x.com/)、[Coinbase](https://www.coinbase.com/)、[Instagram](https://www.instagram.com/) 和 [TikTok](https://www.tiktok.com/) 上的已验证账户。你的应用会收到一个确定性令牌，用于抵御女巫攻击。

即使某个钱包的交易记录寥寥无几，Base Verify 也能根据用户在 X、Instagram 和 TikTok 上的已验证社交账户或 [Coinbase One](https://www.coinbase.com/one) 订阅，判断其是否为高价值用户。这样一来，无论链上活动多寡，你都能识别出优质用户。

**使用场景示例：**

* 代币门控空投或每日奖励
* 专属内容访问 (例如创作者币)
* 基于身份的奖励和会员忠诚度计划

如果你的应用仍需要钱包连接或消息签名功能，请先阅读[验证用户身份](https://docs.cdp.coinbase.com/coinbase-wallet/guides/authenticate-users)、[签名和验证类型化数据](https://docs.cdp.coinbase.com/coinbase-wallet/guides/sign-and-verify-typed-data)或 [Web React 快速入门](https://docs.cdp.coinbase.com/coinbase-wallet/quickstart/web-react)。

## 核心概念 {#core-concepts}

### 提供方 {#provider}

Base Verify 所集成的身份平台。目前支持 **[X](https://x.com/)**、**[Coinbase](https://www.coinbase.com/)**、**[Instagram](https://www.instagram.com/)** 和 **[TikTok](https://www.tiktok.com/)**。

### 验证 {#verification}

一种加密证明，用于证明某个钱包在特定提供方处拥有账户。

### 特征 (Trait) {#trait}

提供方账户中可供验证的特定属性。

**示例：**

* `verified: true` — X 账户已获得蓝色认证标记
* `coinbase_one_active: true` — Coinbase One 订阅处于有效状态
* `followers: gt:1000` — X 账户的关注者超过 1,000 人
* `followers_count: gte:5000` — Instagram 账户的关注者不少于 5,000 人
* `video_count: gte:50` — TikTok 账户发布的视频不少于 50 个

### Action {#action}

由开发者定义的字符串，用于标识用户借助验证所执行的操作。通过 Action，你可以在同一应用中为不同的使用场景签发不同的令牌。

**示例：**

* `claim_daily_reward` — 领取每日奖励
* `join_allowlist` — 加入专属白名单
* `unlock_premium_content` — 访问受限内容
* `participate_in_raffle` — 参与抽奖

#### Action 的工作原理 {#how-actions-work}

Action 通过 [Sign-In with Ethereum (SIWE)](https://eips.ethereum.org/EIPS/eip-4361) 消息中的 resources 字段指定：

```typescript SIWE resources with action
resources: [
  'urn:verify:provider:x',
  'urn:verify:action:claim_daily_reward'
]
```

该 action 会随 API 响应一并返回：

```json Verification response with action
{
  "token": "abc123...",
  "action": "claim_daily_reward",
  "wallet": "0x1234..."
}
```

#### 为什么 Action 很重要 {#why-actions-matter}

**不同的 action 会生成不同的令牌。** 因此，同一个已验证账户可以进行多次相互独立的领取：

* 用户以 action `claim_airdrop` 验证 X 账户 → 令牌：`abc123`
* 同一 X 账户使用 action `join_allowlist` → 令牌：`def456` (不同)
* 同一 X 账户再次使用 action `claim_airdrop` → 令牌：`abc123` (与第一次相同)

**使用场景：**

* **多个活动**——分别开展多个空投，互不干扰
* **功能门控**——为不同的高级功能分配不同的令牌
* **按时间举办的活动**——每次活动使用新的 action (例如 `raffle_jan_2025`、`raffle_feb_2025`)

#### 选择 Action 名称 {#choosing-action-names}

请使用具有描述性的小写名称，单词之间用下划线分隔：

| 推荐                      | 不推荐                             |
| :---------------------- | :------------------------------ |
| `claim_genesis_airdrop` | `airdrop` (过于笼统)                |
| `unlock_pro_features`   | `action1` (没有实际含义)              |
| `enter_weekly_raffle`   | `base_verify_token` (系统保留/易混淆)  |

<Warning>
  action 名称一经上线使用，就不要再更改。更改 action 会为同一批用户生成不同的令牌，导致你的抗女巫攻击机制失效。
</Warning>

### Token — 抗女巫攻击 {#token-sybil-resistance}

一种绑定到提供方账户 (而非钱包) 的确定性标识符。**这是抵御女巫攻击的核心机制。**

#### 工作原理 {#how-it-works}

1. 钱包 A 验证了一个 X 账户 → Base Verify 返回 `Token: abc123` → 你从未见过该令牌，因此发放空投。
2. 同一个 X 账户换用钱包 B 再次尝试 → Base Verify 返回 `Token: abc123` → 你已见过该令牌，因此拦截此次重复领取。

没有 Base Verify，用户就可以换用不同的钱包多次领取。有了 Base Verify，一个已验证账户 = 一个令牌 = 一次领取。

#### 令牌属性 {#token-properties}

* **确定性** — 同一提供方账户始终生成相同的令牌
* **因提供方而异** — 用户的 X 令牌与其 Instagram 令牌不同
* **因应用而异** — 你的应用收到的令牌与其他应用不同 (保护隐私)
* **与 action 绑定** — 令牌会因 SIWE 消息中的 action 不同而变化
* **持久有效** — 令牌不会过期或轮换 (除非用户删除其验证)
* **不受特征影响** — 即使特征发生变化 (例如粉丝数增加) ，令牌也保持不变

#### 如何存储令牌 {#how-to-store-tokens}

```json Verification token storage record
{
  token: "abc123...",
  walletAddress: "0x1234...",
  provider: "x",
  claimedAt: "2024-01-15",
}
```

#### 防止重复领取 {#prevent-double-claims}

```typescript Prevent duplicate claims by token expandable lines
async function claimAirdrop(verificationToken: string, walletAddress: string) {
  const existingClaim = await db.findClaimByToken(verificationToken);

  if (existingClaim) {
    return { error: "This X account already claimed" };
  }

  await db.createClaim({
    token: verificationToken,
    wallet: walletAddress,
    claimedAt: new Date()
  });

  return { success: true };
}
```

### 你的应用需要负责的事项 {#your-apps-responsibilities}

* 生成包含特征要求的 SIWE 消息
* 处理用户钱包连接
* 未找到验证记录时，重定向到 Base Verify App
* 存储返回的验证令牌，防止重复使用
* 在后端妥善保管你的密钥

### Base Verify 的职责 {#base-verifys-responsibilities}

* 验证 SIWE 签名
* 存储来自各提供方的验证信息 (X、Coinbase、Instagram、TikTok)
* 检查验证结果是否满足特征 (trait) 要求
* 协助完成与提供方之间的 OAuth 流程
* 返回确定性令牌，用于抵御女巫攻击

### 响应码 {#response-codes}

| 代码                                                        | 含义                               | 操作                       |
| :-------------------------------------------------------- | :------------------------------- | :----------------------- |
| **200 OK**                                                | 钱包已验证该提供方账户，并且满足所有特征要求。返回一个唯一令牌。 | 授予访问权限，并存储该令牌。           |
| **404 Not Found**                                         | 钱包从未验证过该提供方。                     | 将用户重定向到 Base Verify App。 |
| **400 Bad Request** (`verification_traits_not_satisfied`) | 钱包已验证该提供方，但不满足特征要求。              | 提示用户其不满足要求。**不要**重定向。    |

## 快速入门 {#getting-started}

### 前提条件 {#prerequisites}

1. **API 密钥** — 填写[意向表单](https://forms.gle/6L4hWAHkojYcefz27)以获取访问权限
2. **钱包集成** — 用户必须能够连接钱包并签署消息。请参阅[验证用户身份](https://docs.cdp.coinbase.com/coinbase-wallet/guides/authenticate-users)或 [Web React 快速入门](https://docs.cdp.coinbase.com/coinbase-wallet/quickstart/web-react)
3. **后端服务器** — 用于安全地调用 Base Verify API，并妥善保管你的密钥。如需了解类似的前端到后端签名模式，请参阅[签名和验证类型化数据](https://docs.cdp.coinbase.com/coinbase-wallet/guides/sign-and-verify-typed-data)

### 注册你的应用 {#register-your-app}

请向 Base Verify 团队提供以下信息：

1. 你的**应用域名**
2. 你的**重定向 URI**——用户完成验证后跳转回的地址 (例如 `https://yourapp.com`)

<Warning>
  你的密钥**绝不能**暴露在前端代码中。所有 Base Verify API 调用都必须经由你的后端发起。
</Warning>

## 实现 {#implementation}

<Steps>
  <Step title="配置应用">
    为你的 Base Verify 集成创建配置文件：

    ```typescript lib/config.ts highlight={3}
    export const config = {
      appUrl: 'https://your-app.com',
      baseVerifySecretKey: process.env.BASE_VERIFY_SECRET_KEY,
      baseVerifyApiUrl: 'https://verify.base.dev/v1',
      baseVerifyMiniAppUrl: 'https://verify.base.dev',
    }
    ```

    将你的密钥添加到 `.env.local` 中：

    ```shell .env.local
    BASE_VERIFY_SECRET_KEY=your_secret_key_here
    ```
  </Step>

  <Step title="生成 SIWE 签名（前端）">
    构建一条 [SIWE](https://eips.ethereum.org/EIPS/eip-4361) 消息，其中包含提供方、特征要求和操作：

    ```typescript lib/signature-generator.ts expandable lines highlight={7-12,15-24}
    import { SiweMessage, generateNonce } from 'siwe'
    import { config } from './config'

    export async function generateSignature(
      signMessageFunction: (message: string) => Promise<string>,
      address: string
    ) {
      const resources = [
        'urn:verify:provider:x',
        'urn:verify:provider:x:verified:eq:true',
        'urn:verify:provider:x:followers:gte:100',
        'urn:verify:action:claim_airdrop'
      ]

      const siweMessage = new SiweMessage({
        domain: new URL(config.appUrl).hostname,
        address,
        statement: 'Verify your X account',
        uri: config.appUrl,
        version: '1',
        chainId: 8453,
        nonce: generateNonce(),
        issuedAt: new Date().toISOString(),
        expirationTime: new Date(Date.now() + 6 * 60 * 60 * 1000).toISOString(),
        resources,
      })

      const message = siweMessage.prepareMessage()
      const signature = await signMessageFunction(message)

      return { message, signature, address }
    }
    ```
  </Step>

  <Step title="检查验证结果（前端 → 后端）">
    前端生成签名后发送到**您自己的**后端，再由后端调用 Base Verify API。

    **前端：**

    ```typescript Frontend verification check expandable lines highlight={2-8,11-19}
    async function checkVerification(address: string) {
      const signature = await generateSignature(
        async (msg) => {
          return new Promise((resolve, reject) => {
            signMessage(
              { message: msg },
              { onSuccess: resolve, onError: reject }
            )
          })
        },
        address
      )

      const response = await fetch('/api/check-verification', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
        },
        body: JSON.stringify({
          signature: signature.signature,
          message: signature.message,
          address: address
        })
      })

      const data = await response.json();
      return data;
    }
    ```

    **后端 (你的 API 端点) ：**

    ```typescript pages/api/check-verification.ts expandable lines highlight={5-8,15,19-24}
    import { validateTraits } from '../../lib/trait-validator';

    export default async function handler(req, res) {
      const { signature, message, address } = req.body;

      const expectedTraits = {
        'verified': 'true',
        'followers': 'gte:100'
      };

      const validation = validateTraits(message, 'x', expectedTraits);

      if (!validation.valid) {
        return res.status(400).json({
          error: 'Invalid trait requirements in message',
          details: validation.error
        });
      }

      const response = await fetch('https://verify.base.dev/v1/base_verify_token', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          'Authorization': `Bearer ${process.env.BASE_VERIFY_SECRET_KEY}`,
        },
        body: JSON.stringify({
          signature: signature,
          message: message,
        })
      });

      if (response.ok) {
        const data = await response.json();
        return res.status(200).json({ verified: true, token: data.token });
      } else if (response.status === 404) {
        return res.status(404).json({ verified: false, needsVerification: true });
      } else if (response.status === 400) {
        const data = await response.json();
        if (data.message === 'verification_traits_not_satisfied') {
          return res.status(400).json({ verified: false, traitsNotMet: true });
        }
      }

      return res.status(500).json({ error: 'Verification check failed' });
    }
    ```

    <Warning>
      你的后端**必须**校验 SIWE 消息中的特征要求是否与后端预期一致，以防止用户在前端篡改特征要求来绕过你的访问控制。详情请参阅[安全最佳实践](#validate-trait-requirements)。
    </Warning>
  </Step>

  <Step title="跳转至 Base Verify（前端）">
    如果收到 404 响应，请将用户重定向到 Base Verify App 以完成 OAuth 授权：

    ```typescript Open the Base Verify App lines wrap expandable highlight={3-6,9}
    function redirectToVerifyMiniApp(provider: string) {
      const params = new URLSearchParams({
        redirect_uri: config.appUrl,
        providers: provider,
      })

      const miniAppUrl = `${config.baseVerifyMiniAppUrl}?${params.toString()}`

      const deepLink = `cbwallet://miniapp?url=${encodeURIComponent(miniAppUrl)}`
      window.open(deepLink, '_blank')
    }
    ```

    验证完成后，用户会带着 `?success=true` 跳转回你的 `redirect_uri`。此时再次执行检查 (第 3 步) ，就会返回 200 和一个令牌。如果你正在为 Base app 开发应用，请参阅 [Build on Base 概览](/zh/build-on-base/overview)，了解有关应用结构和生命周期的更全面指南。
  </Step>
</Steps>

### 错误处理 {#error-handling}

| 响应                                            | 处理方式                              |
| :-------------------------------------------- | :-------------------------------- |
| **404**                                       | 用户尚未完成验证。将其重定向到 Base Verify App。  |
| **400** (`verification_traits_not_satisfied`) | 用户已有账户，但不满足要求。显示提示信息，不要重定向，也不要重试。 |
| **200**                                       | 存储令牌并授予访问权限。                      |

<Note>
  **不要**重试 404 响应，这只是表示用户尚未完成验证。也**不要**重试带有 `verification_traits_not_satisfied` 的 400 响应：除非用户的账户指标发生变化 (例如粉丝数增加) ，否则重试也无济于事。
</Note>

## API 参考 {#api-reference}

### 身份验证 {#authentication}

所有 API 请求都必须在 `Authorization` 请求头中携带您的密钥：

```http Authorization header
Authorization: Bearer YOUR_SECRET_KEY
```

### POST /v1/base_verify_token {#post-v1base_verify_token}

检查钱包是否具有特定的验证，并获取相应的验证令牌。

#### 请求 {#request}

```json POST /v1/base_verify_token request body
{
  signature: string,   // 钱包生成的 SIWE 签名
  message: string      // SIWE 消息（resources 中包含 provider/traits）
}
```

#### 请求示例 {#example-request}

```bash POST /v1/base_verify_token cURL example wrap
curl -X POST https://verify.base.dev/v1/base_verify_token \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_SECRET_KEY" \
  -d '{
    "signature": "0x1234...",
    "message": "verify.base.dev wants you to sign in..."
  }'
```

#### 响应 {#responses}

**200 OK — 验证通过：**

```json 200 OK response
{
  "token": "abc123...",
  "action": "claim_airdrop",
  "wallet": "0x1234..."
}
```

| 字段       | 类型     | 描述                                                       |
| :------- | :----- | :------------------------------------------------------- |
| `token`  | string | 用于抵御女巫攻击 (Sybil) 的确定性验证令牌。相同的提供方账户 + 相同的 action = 相同的令牌。 |
| `action` | string | SIWE 消息中指定的自定义 action。不同的 action 会生成不同的令牌。               |
| `wallet` | string | 用户的钱包地址。                                                 |

**404 Not Found — 未找到验证记录：**

```json 404 not found response
{
  "error": "verification_not_found"
}
```

将用户重定向至 Base Verify App 以完成验证。

**400 Bad Request — 不满足 trait 条件：**

```json 400 traits not satisfied response
{
  "code": 9,
  "message": "verification_traits_not_satisfied",
  "details": []
}
```

用户拥有该提供方账户，但不满足特征要求。请勿进行重定向。

**401 Unauthorized — 密钥无效：**

```json 401 unauthorized response
{
  "error": "unauthorized"
}
```

请检查您的密钥是否正确，并确认已将其添加到 Authorization 请求头中。

### 应用重定向 {#app-redirect}

要将用户重定向到 Base Verify 进行验证，请执行以下操作：

```text Base Verify redirect URL format
https://verify.base.dev?redirect_uri={your_app_url}&providers={provider}
```

| 参数             | 必填 | 说明              | 示例                                     |
| :------------- | :- | :-------------- | :------------------------------------- |
| `redirect_uri` | 是  | 验证完成后将用户重定向到的地址 | `https://yourapp.com`                  |
| `providers`    | 是  | 要验证的提供方         | `x`, `coinbase`, `instagram`, `tiktok` |

## 特征目录 {#trait-catalog}

特征 (Trait) 是提供方账户中可供验证的特定属性，在 [SIWE](https://eips.ethereum.org/EIPS/eip-4361) 消息的 resources 中指定，格式如下：

```text Trait resource format
urn:verify:provider:{provider}:{trait_name}:{operation}:{value}
```

### 运算符 {#operations}

| 运算符       | 符号    | 适用类型 | 说明           | 示例                                 |
| :-------- | :---- | :--- | :----------- | :--------------------------------- |
| 等于        | `eq`  | 所有类型 | 精确匹配         | `verified:eq:true`                 |
| 大于        | `gt`  | 整数   | 严格大于         | `followers:gt:1000`                |
| 大于等于      | `gte` | 整数   | 大于或等于        | `followers:gte:1000`               |
| 小于        | `lt`  | 整数   | 严格小于         | `followers:lt:5000`                |
| 小于等于      | `lte` | 整数   | 小于或等于        | `followers:lte:5000`               |
| 包含于 (列表)  | `in`  | 字符串  | 值位于以逗号分隔的列表中 | `verified_type:in:blue,government` |

### 类型系统 {#type-system}

**布尔型特征：**

* 取值：`"true"` 或 `"false"` (字符串形式)
* 仅支持 `eq` 运算符
* 示例：`verified:eq:true`

**整数型特征：**

* 取值：以字符串表示的数字
* 支持的运算符：`eq`、`gt`、`gte`、`lt`、`lte`
* 示例：`followers:gte:1000`

**字符串型特征：**

* 取值：文本字符串
* 支持的运算符：`eq`、`in`
* 示例：`verified_type:eq:blue` 或 `verified_type:in:blue,government`

### 组合特征 {#combining-traits}

为同一提供方指定多个特征时，这些特征必须**全部**满足 (AND 逻辑) ：

```typescript Multiple traits for one provider
resources: [
  'urn:verify:provider:x',
  'urn:verify:provider:x:verified:eq:true',
  'urn:verify:provider:x:followers:gte:10000'
]
```

<Note>
  每个请求只能检查一个提供方。如需检查多个提供方，请分别调用 API。
</Note>

### 常见模式 {#common-patterns}

**分级访问：**

## 安全与隐私 {#security-and-privacy}

### SIWE 签名要求 {#siwe-signature-requirement}

每次 API 调用都需要钱包所有者提供有效的 [SIWE](https://eips.ethereum.org/EIPS/eip-4361) 签名。这样可以防止：

* 任意查询验证状态
* 第三方查看某个钱包是否已通过验证
* 枚举攻击

用户需签署一条结构化消息，以证明自己控制该钱包，并同意对特定属性进行检查：

```json SIWE payload example lines wrap expandable
{
  domain: "your-app.com",
  address: "0x1234...",
  chainId: 8453,
  resources: [
    "urn:verify:provider:x",
    "urn:verify:provider:x:verified:eq:true",
    "urn:verify:action:claim_airdrop"
  ]
}
```

### 验证特征要求 {#validate-trait-requirements}

<Warning>
  当后端收到来自前端的 SIWE 消息时，你**必须**验证消息中的特征要求是否与后端的预期一致，以防用户在前端篡改特征要求，绕过你的访问控制。
</Warning>

**缺少验证时的攻击示例：**

1. 你的应用要求用户拥有 100 名关注者
2. 用户篡改前端，只请求 10 名关注者
3. 用户对篡改后的消息进行签名
4. 由于缺少验证，后端将该请求转发给 Base Verify
5. 用户在关注者不足 100 名的情况下获得了访问权限

**实现：**

```typescript Validate traits on the backend lines wrap expandable highlight={2-4,7}
import { validateTraits } from './lib/trait-validator';

const expectedTraits = {
  'followers': 'gte:100'
};

const validation = validateTraits(message, 'x', expectedTraits);

if (!validation.valid) {
  return res.status(400).json({
    error: 'Invalid trait requirements in message',
    details: validation.error
  });
}
```

### 保护你的密钥 {#protect-your-secret-key}

**切勿：**

* 在前端代码中包含密钥
* 使用 `NEXT_PUBLIC_*` 或其他会暴露给浏览器的环境变量
* 将密钥提交到版本控制系统
* 通过聊天、电子邮件或文档分享密钥

**务必：**

* 仅将密钥存储在后端环境变量中
* 使用已加入 gitignore 的 `.env` 文件
* 密钥一旦意外泄露，立即轮换
* 仅从后端调用 Base Verify API

### OAuth 安全模型 {#oauth-security-model}

Base Verify 通过 [OAuth](https://oauth.net/2/) 验证提供方账户：

1. 用户在 Base Verify App 中发起 OAuth 授权
2. 提供方 (X、Instagram 等) 对用户进行身份验证
3. 提供方向 Base Verify 返回 OAuth 令牌
4. Base Verify 使用该 OAuth 令牌获取账户数据
5. Base Verify 存储验证记录，并将其与用户钱包关联
6. OAuth 令牌经加密后安全存储

你的应用无需处理 OAuth 令牌或重定向——这些全部由 Base Verify App 完成。

### 数据存储 {#data-storage}

**Base Verify 会存储的内容：**

* 与已验证提供方账户关联的钱包地址
* 提供方账户元数据 (用户名、粉丝数、认证状态)
* OAuth 令牌 (加密存储，绝不与应用共享)
* 验证时间戳

**Base Verify 不会存储的内容：**

* 用户私钥
* 提供方账户密码
* 用户活动或浏览记录
* 验证所需之外的任何数据

**你的应用会收到的内容：**

调用 `/v1/base_verify_token` 时，你只会收到 `token`、`action` 和 `wallet`，不会返回任何个人身份信息 (PII) 。

### 用户控制 {#user-control}

用户可以随时删除其验证记录：

* 删除所有已存储的提供方数据
* 此后无法再生成令牌
* 你的应用已存储的令牌将不再具有意义 (用户无法使用同一账户重新验证)

### 缓存 {#caching}

缓存验证结果，以减少 API 调用次数：

* 仅在用户会话期间缓存 (不要永久缓存)
* 用户断开钱包连接时清除缓存
* 不要在每次加载页面时都检查验证状态
